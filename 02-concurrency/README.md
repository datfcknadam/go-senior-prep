# 02. Конкурентность

Самая важная тема для Go-собеседования. На senior ожидают не «знаю, что такое канал», а умение
написать конкурентный код без гонок, утечек и дедлоков **и объяснить, почему он корректен**.

> Подробно: [THEORY.md](THEORY.md) — каналы и select изнутри, sync, атомики, memory model, паттерны с кодом.

## Горутины

- Стартовый стек ~2 КБ, растёт копированием (contiguous stacks). Создание — сотни наносекунд.
- Горутину нельзя убить снаружи — только попросить завершиться (`context`, закрытый канал).
- **Утечка горутин** — главная проблема: горутина навсегда заблокирована на канале или ждёт контекста, которого никто не отменит.
  Правило: у каждой горутины, которую ты запускаешь, должен быть понятный путь завершения, и кто-то должен его дождаться.
- Ловить утечки в тестах: `go.uber.org/goleak`; в проде — метрика `go_goroutines` и `pprof/goroutine`.

## Каналы

- Внутри: `hchan` — кольцевой буфер, мьютекс, очереди ждущих отправителей и получателей (`sudog`).
- Таблица поведения (её надо знать наизусть):

| Операция | nil-канал | закрытый | открытый |
|---|---|---|---|
| `ch <- v` | блок навсегда | **panic** | блок / успех |
| `<-ch` | блок навсегда | нулевое значение, `ok=false` | блок / успех |
| `close(ch)` | **panic** | **panic** | успех |

- Канал закрывает **отправитель**, и только когда больше отправлять некому. Несколько отправителей — закрывает тот, кто дождался их всех (`WaitGroup`).
- Небуферизованный канал — точка синхронизации (happens-before между отправкой и приёмом).
- Буфер — не способ «починить» дедлок, а инструмент сглаживания неравномерной нагрузки.

## sync

- `Mutex` — с режимом голодания (starvation mode): если ждущий ждёт > 1 мс, мьютекс передаётся по очереди (FIFO).
- `RWMutex` — выигрывает, только когда чтений гораздо больше и критическая секция заметная. Иначе обычный `Mutex` быстрее.
- `WaitGroup`, `Once` / `OnceFunc` / `OnceValue`, `Cond` (редко нужен), `Pool` (переиспользование буферов, очищается при GC).
- `sync.Map` — оптимизирован для двух сценариев: ключ пишется один раз и много читается, либо горутины работают с непересекающимися ключами. В остальных случаях — `map` + `Mutex`.
- `atomic` — `atomic.Int64`, `atomic.Pointer[T]`. CAS-циклы.
- Шардирование мьютексов — частый ответ на «как убрать contention».

## context

- Отмена распространяется **вниз** по дереву. `Done()` закрывается при отмене или дедлайне.
- `cancel` вызывать всегда (`defer cancel()`), иначе утечка таймера и ресурсов до отмены родителя.
- `context.WithoutCancel`, `context.AfterFunc`, `context.WithCancelCause` (Go 1.20–1.21).
- `context.Value` — только для request-scoped данных (trace id, user), не для передачи зависимостей.

## Memory model

- Без синхронизации нет гарантий видимости между горутинами. Гонка данных = неопределённое поведение (вплоть до порванных интерфейсов).
- happens-before дают: операции с каналами, `Mutex`, `Once`, `WaitGroup`, `atomic`.
- `go test -race` — обязательная часть CI. Детектор находит только реально случившиеся гонки.

## Паттерны (знать и уметь написать за 10 минут)

- worker pool, fan-out / fan-in, pipeline
- `errgroup` с лимитом (`g.SetLimit(n)`), отмена при первой ошибке
- семафор на буферизованном канале
- rate limiter (token bucket), `singleflight`
- graceful shutdown: `signal.NotifyContext` → `server.Shutdown(ctx)` → дождаться воркеров
