# Теория: конкурентность — подробно

Расширенная версия [README](README.md). На senior-интервью по конкурентности обычно идут три блока:
внутреннее устройство (каналы, мьютексы, планировщик), live coding (пул, fan-in, rate limiter) и ревью кода с гонками и утечками.

---

## 1. Конкурентность и параллелизм

- **Конкурентность** — это структура программы: независимые задачи, которые чередуются. **Параллелизм** — физически одновременное
  выполнение на нескольких ядрах. Go даёт конкурентность, а параллелизм ограничен `GOMAXPROCS`.
- Модель Go — CSP: «не общайтесь через разделяемую память, разделяйте память через общение».
  На практике каналы применяют для передачи владения и сигналов, а мьютексы — для защиты состояния. Нормально использовать и то и другое.

---

## 2. Горутины

- Горутина — это структура `g` в рантайме: стек (стартует с 2 КБ, растёт копированием), регистры, статус.
  Переключение между ними происходит в user space и стоит десятки–сотни наносекунд, против микросекунд у потоков ОС.
- Миллион горутин — нормально, это ~2–4 ГБ стеков в худшем случае. Но **ограничивать параллелизм всё равно нужно**:
  узкое место переезжает в БД, в сеть или в лимиты внешнего API.
- У горутины нет ID в публичном API, её нельзя убить снаружи, и она не возвращает значение. Результат и ошибку отдают через канал, `errgroup` или общую структуру под мьютексом.
- **Утечка горутины** — горутина, которая никогда не завершится. Типичные причины:
  - отправка в канал, который никто не читает (читатель ушёл по таймауту);
  - чтение из канала, который никто не закроет;
  - ожидание `ctx.Done()` у контекста, который никто не отменит (`context.Background()`);
  - забытый `ticker.Stop()` (до 1.23 тикер держался в памяти).
  ```go
  // Классическая утечка: при таймауте горутина навсегда застрянет на отправке.
  ch := make(chan result)        // фикс: make(chan result, 1)
  go func() { ch <- slowCall() }()
  select {
  case r := <-ch: return r
  case <-time.After(time.Second): return timeoutErr
  }
  ```
- **Правило владельца:** кто запустил горутину, тот отвечает за её остановку и ожидание. Запускать её «в фоне и забыть» нельзя.

## 3. Каналы изнутри

```go
type hchan struct {
    qcount   uint           // элементов в буфере
    dataqsiz uint           // размер буфера
    buf      unsafe.Pointer // кольцевой буфер
    elemsize uint16
    closed   uint32
    sendx, recvx uint       // индексы кольца
    recvq, sendq waitq      // очереди ждущих горутин (sudog)
    lock     mutex
}
```

- **Отправка:**
  1. Если в `recvq` есть ждущий получатель, значение копируется **прямо в его стек**, минуя буфер, и получатель будится.
  2. Иначе, если в буфере есть место, значение кладётся в буфер.
  3. Иначе горутина паркуется в `sendq`.
- **Приём** работает симметрично. Если буфер полон и есть ждущий отправитель, получатель берёт голову буфера, а значение отправителя кладётся в хвост
  (так сохраняется FIFO).
- `close` будит **всех** ждущих: получатели получают нулевое значение, отправители — panic.
- Канал защищён мьютексом, так что это не lock-free структура. Под высокой конкуренцией канал медленнее мьютекса и атомика.
  Каналы нужны ради семантики, а не ради скорости.
- **Таблица (наизусть):**

| Операция | nil | закрытый | открытый |
|---|---|---|---|
| `ch <- v` | блок навсегда | panic | блок или успех |
| `<-ch` | блок навсегда | zero value, `ok=false` | блок или успех |
| `close` | panic | panic | ок |
| `len`/`cap` | 0 | работают | работают |

- **Правила закрытия:** закрывает отправитель. Если отправителей несколько, закрывает координатор после `wg.Wait()`.
  Закрытие нужно, только когда получателю необходимо узнать «больше ничего не будет», например для `range`. Канал — не файл, GC соберёт и незакрытый.
- **Направленные каналы** `chan<- T` и `<-chan T` в сигнатурах документируют владение, и компилятор их проверяет.
- `chan struct{}` + `close` — широковещательный сигнал всем горутинам (так устроен `ctx.Done()`).

## 4. select

- Если готовы несколько веток, выбирается **случайная** (равномерно). Это защита от голодания, порядок веток не задаёт приоритет.
- `default` делает select неблокирующим: try-send или try-recv.
- **nil-канал в select** выключает ветку. Это идиома для слияния каналов, которые закрываются в разное время:
  ```go
  for a != nil || b != nil {
      select {
      case v, ok := <-a: if !ok { a = nil; continue }; out <- v
      case v, ok := <-b: if !ok { b = nil; continue }; out <- v
      }
  }
  ```
- **Приоритет** делается вложенным select: сначала неблокирующая проверка `ctx.Done()`, затем основной select.
- Пустой `select {}` блокирует навсегда.
- **Таймауты:** `time.After` в цикле создаёт новый таймер на каждой итерации. С 1.23 они собираются GC, но в горячем цикле
  всё равно лучше один `time.NewTimer` + `Reset`. Внешнюю операцию лучше ограничивать через `context.WithTimeout`.
- Важная деталь: при `case out <- compute():` выражение `compute()` вычисляется **до** выбора ветки, даже если ветка не будет выбрана.

## 5. Пакет sync

### Mutex
- Состояние — `int32` (locked, woken, starving, счётчик ждущих) + семафор.
- **Нормальный режим:** пришедшая горутина может «перехватить» мьютекс у разбуженной, потому что она уже на CPU и это выгодно для throughput.
  Перед парковкой возможен короткий спин, если ядер > 1 и есть работающие P.
- **Режим голодания:** если ждущий ждёт > 1 мс, мьютекс передаётся строго по очереди, а новые горутины не спинят и встают в хвост.
  Выход из режима — когда ждущий последний или ждал < 1 мс.
- Мьютекс не реентерабелен: повторный `Lock` в той же горутине даёт дедлок. Владельца у мьютекса нет, разблокировать можно из другой горутины, но так не делают.
- `TryLock` (1.18) есть, но его использование почти всегда признак плохого дизайна.

### RWMutex
- Много читателей или один писатель. **Писатель в приоритете:** после `Lock()` новые `RLock()` ждут, иначе писатель голодал бы.
  Поэтому **рекурсивный `RLock` может дать дедлок**, если между двумя вызовами пришёл писатель.
- Он дороже `Mutex` (атомики на счётчике читателей, cache-line contention на многих ядрах). Выигрывает только при редких записях и **длинной** секции чтения.

### WaitGroup
- `Add` вызывай **до** `go`, а не внутри горутины, иначе `Wait` может проскочить. С Go 1.25 есть `wg.Go(func(){...})`, который делает это сам.
- Счётчик ниже нуля даёт panic. Повторно использовать можно только после возврата `Wait`.

### Once, OnceFunc, OnceValue(s)
- `Once.Do` гарантирует, что f выполнится один раз, а **все** вызвавшие дождутся её окончания: внутри fast-path на атомике и slow-path на мьютексе.
  Если f запаниковала, Once считается выполненным.
- `sync.OnceValue(func() (T))` и `OnceValues` (1.21) удобны для ленивой инициализации синглтонов.

### Cond
- Ожидание условия: `for !cond { c.Wait() }`, всегда в цикле, потому что бывают ложные пробуждения и проверка условия под локом обязательна.
  На практике его почти всегда заменяет канал. Знать нужно, писать редко.

### Pool
- Кеш временных объектов для снижения аллокаций (буферы, encoder'ы). Устроен как локальные пулы на каждый P (без локов) + victim cache:
  при GC содержимое переезжает в victim, а при следующем GC пропадает.
- Объекты могут исчезнуть в любой момент. Пул — **не** пул соединений.
- Класть нужно указатели (`*bytes.Buffer`), иначе при упаковке в `any` получится аллокация. Перед `Put` делай `Reset`.
  Огромные буферы обратно не клади (как в `fmt`), иначе пул раздуется.

### sync.Map
- Рассчитан на два сценария: ключи пишутся один раз и много читаются (кеш), либо горутины работают с непересекающимися наборами ключей.
- С Go 1.24 внутри concurrent hash-trie (`HashTrieMap`), раньше было read-only map + dirty map с промоутом.
- В остальных случаях `map` + `Mutex`/`RWMutex` или шардированная мапа (N кусков по хешу ключа) быстрее и типобезопаснее.

## 6. Атомики и lock-free

- `sync/atomic`: `atomic.Int64`, `atomic.Bool`, `atomic.Pointer[T]`, `atomic.Value`. Операции `Load`, `Store`, `Add`, `Swap`, `CompareAndSwap`, с 1.23 ещё `And`/`Or`.
- В Go атомики **последовательно согласованы** (seq-cst). Слабых порядков, как в C++, нет.
- **CAS-цикл:**
  ```go
  for {
      old := v.Load()
      if v.CompareAndSwap(old, old*2) { break }
  }
  ```
- **Copy-on-write конфиг:** `atomic.Pointer[Config]`. Читатели делают `Load()` без локов, писатель собирает новый объект и делает `Store()`.
  Это популярный ответ на «как обновлять конфиг или правила без блокировок».
- **False sharing:** два атомика, которые часто пишутся из разных ядер, лежат в одной кеш-линии (64 байта) и мешают друг другу.
  Лечится паддингом `_ [56]byte` или `cpu.CacheLinePad`.
- Атомик защищает **одну** переменную. Инвариант между двумя переменными требует мьютекса.

## 7. context

- Интерфейс: `Deadline()`, `Done() <-chan struct{}`, `Err()`, `Value(key)`. Контексты образуют **дерево**, и отмена идёт от родителя к детям.
- `cancelCtx` хранит мапу детей. При `cancel()` он закрывает `done` и рекурсивно отменяет детей. `WithTimeout`/`WithDeadline` дополнительно держат `time.Timer`.
- **`defer cancel()` обязателен.** Без него ребёнок висит в мапе родителя и держит таймер до отмены родителя, а это утечка.
- `Err()` возвращает `context.Canceled` или `context.DeadlineExceeded`. С 1.20 есть `WithCancelCause` + `context.Cause(ctx)`, чтобы узнать *почему*.
- `context.WithoutCancel(ctx)` (1.21) сохраняет значения, но не наследует отмену. Пример: запустить фоновую запись аудита после ответа клиенту.
- `context.AfterFunc(ctx, f)` (1.21) вызывает f при отмене. Удобно, чтобы прервать блокирующий вызов, который не понимает контекст.
- `Value`: поиск идёт **линейно вверх по цепочке**, это O(глубины). Ключ — неэкспортируемый тип, чтобы не было коллизий.
  Кладут туда request-scoped данные (trace id, user id, логгер), но **не** зависимости и не опциональные параметры функций.
- **Правила:** `ctx` — первый аргумент, его не хранят в структурах (исключение — объекты, привязанные к одному запросу). `nil` вместо ctx не передают.
- **Проверка отмены в CPU-цикле:** `select { case <-ctx.Done(): return ctx.Err(); default: }` раз в N итераций.

## 8. Memory model

- Формально (пересмотрена в 1.19): программа без гонок данных ведёт себя последовательно согласованно (**DRF-SC**).
  Гонка данных — это конкурентный доступ к одной ячейке, где хотя бы один доступ на запись и между ними нет happens-before.
- **Отношение happens-before дают:**
  - `go f()` happens-before начала `f`;
  - отправка в канал happens-before завершения соответствующего приёма;
  - `close(ch)` happens-before приёма, который вернул zero value из-за закрытия;
  - для **небуферизованного** канала: приём happens-before завершения отправки;
  - для буферизованного ёмкости C: k-й приём happens-before завершения (k+C)-й отправки (так работает семафор на канале);
  - `Unlock` happens-before следующего `Lock`; `Once.Do(f)`: завершение f happens-before возврата любого `Do`;
  - атомики: если `Load` увидел значение `Store`, то `Store` happens-before `Load`.
- **Классические ошибки:**
  ```go
  var done bool
  go func() { work(); done = true }()
  for !done {}            // может крутиться вечно: компилятор вправе вынести чтение из цикла
  ```
  ```go
  if instance == nil {    // double-checked locking без атомика — гонка
      mu.Lock(); if instance == nil { instance = new(T) }; mu.Unlock()
  }
  ```
- Гонка на интерфейсе или слайсе (составные слова) может дать **порванное значение**: тип от одного, данные от другого, а дальше segfault или произвольное поведение.
  Поэтому «безобидных» гонок в Go не бывает.
- **Race detector** (`-race`) построен на ThreadSanitizer. Замедляет в 2–20 раз и ест в 5–10 раз больше памяти. Видит только гонки, которые **случились** при прогоне,
  так что нужны тесты с реальной конкуренцией. В CI обязателен, в проде его не включают.

## 9. Дедлоки и livelock

- Рантайм ловит только тотальный дедлок: `fatal error: all goroutines are asleep - deadlock!`. Если хоть одна горутина жива
  (HTTP-сервер, таймер), частичный дедлок **не диагностируется**.
- Типичные причины: два мьютекса захватываются в разном порядке (лечится глобальным порядком, например по id, см. задачу `bank`);
  отправка в канал под мьютексом, пока читатель ждёт этот мьютекс; рекурсивный `RLock`; `wg.Wait()` внутри горутины, которую сам ждёшь.
- Диагностика в проде: `pprof/goroutine?debug=2` (стеки и время в ожидании), профили `mutex` и `block`.
- **Тестирование времени:** `testing/synctest` (1.25) запускает код в «пузыре» с виртуальными часами. Можно детерминированно проверить таймауты
  и ретраи без `time.Sleep` в тестах.

## 10. Паттерны (уметь написать с нуля)

### Генератор + отмена
```go
func gen(ctx context.Context, n int) <-chan int {
    out := make(chan int)
    go func() {
        defer close(out)
        for i := range n {
            select {
            case out <- i:
            case <-ctx.Done():
                return
            }
        }
    }()
    return out
}
```
Каждая отправка стоит в select с `ctx.Done()`. Это главный приём против утечек.

### Worker pool
Пул из N воркеров читает из канала задач и пишет в канал результатов. Канал результатов закрывает отдельная горутина после `wg.Wait()`.
Вопросы, которые зададут: как сохранить порядок (результат с индексом и запись в слайс по индексу), как остановиться на первой ошибке (ctx + cancel или errgroup),
что будет, если читатель результатов ушёл (воркеры должны слушать ctx).

### errgroup — самый практичный инструмент
```go
g, ctx := errgroup.WithContext(ctx)
g.SetLimit(10)
for _, id := range ids {
    g.Go(func() error { return process(ctx, id) })
}
return g.Wait() // первая ошибка; ctx отменится для остальных
```
Ограничение: результаты собирай сам. Пиши в `results[i]` по индексу, и тогда мьютекс не нужен, потому что индексы разные.

### Семафор
`sem := make(chan struct{}, n)`: `sem <- struct{}{}` перед работой, `<-sem` после. Вариант со взвешенными и контекстными разрешениями: `golang.org/x/sync/semaphore`.

### Pipeline
Стадии соединены каналами, каждая стадия закрывает свой выход и слушает ctx. Пропускная способность определяется самой медленной стадией.
Масштабируют её fan-out (несколько воркеров на стадии), а потом делают fan-in.

### Rate limiting
- Token bucket: ведро ёмкостью B, пополняется со скоростью r. Разрешает всплески до B. Реализация: `golang.org/x/time/rate`.
- Leaky bucket — ровный поток. Fixed window даёт проблему на границе окна. Sliding window log/counter точнее.
- Распределённый лимит: Redis + Lua (атомарно) или GCRA.

### singleflight
Схлопывает одинаковые одновременные запросы в один. Защищает от cache stampede. Подвох: если запрос завис, ждут все,
поэтому нужен таймаут, `DoChan` или `Forget`.

### Graceful shutdown
```go
ctx, stop := signal.NotifyContext(context.Background(), syscall.SIGINT, syscall.SIGTERM)
defer stop()
go srv.ListenAndServe()
<-ctx.Done()
shutdownCtx, cancel := context.WithTimeout(context.Background(), 15*time.Second)
defer cancel()
srv.Shutdown(shutdownCtx) // перестаёт принимать, ждёт активные запросы
// затем: остановить консьюмеры → дождаться воркеров → flush метрик и логов → закрыть БД
```
В Kubernetes: при SIGTERM readiness-проба сначала падает, затем идёт пауза, чтобы endpoints успели обновиться, и только потом Shutdown.
Порядок остановки обратен порядку запуска.

## 11. Чек-лист ревью конкурентного кода

Эти пункты ищет интервьюер на этапе code review:

- [ ] У каждой горутины есть путь завершения, и кто-то её дожидается.
- [ ] Каждая блокирующая отправка или приём стоит в select с `ctx.Done()`.
- [ ] Канал закрывает отправитель, ровно один раз.
- [ ] `wg.Add` стоит до `go`.
- [ ] Нет доступа к мапе или слайсу из нескольких горутин без синхронизации, включая `append` в общий слайс.
- [ ] Мьютексы не копируются (ресиверы — указатели).
- [ ] Под мьютексом нет IO, сетевых вызовов и блокирующих операций с каналами.
- [ ] Порядок захвата нескольких локов фиксирован.
- [ ] `cancel()` от `WithCancel`/`WithTimeout` вызывается всегда.
- [ ] Параллелизм ограничен (пул, семафор, `SetLimit`), а не «горутина на каждый элемент из запроса».
- [ ] Паника в фоновой горутине не уронит процесс (recover + лог + метрика).
- [ ] Тесты гоняются с `-race`, а время в тестах управляемое.
