# 06. System Design

Для senior это часто решающий этап. Оценивают не «правильную архитектуру» (её нет), а то, как ты
**выясняешь требования, считаешь, выбираешь и обосновываешь компромиссы, видишь точки отказа**.

## Каркас на 45–60 минут

| Этап | Время | Что делать |
|---|---|---|
| 1. Требования | 5–7 мин | Функциональные (что делает, 3–5 сценариев). Нефункциональные: RPS, латентность (p99), доступность, консистентность, объём данных. **Явно сказать, что не делаем.** |
| 2. Оценка | 3–5 мин | DAU → RPS (средний и пиковый), чтение/запись, объём хранения за год, трафик. Порядки, а не точные цифры. |
| 3. API | 5 мин | Основные эндпоинты / gRPC-методы, пагинация, идемпотентность. |
| 4. Модель данных | 5–7 мин | Сущности, ключи, выбор хранилища, индексы, ключ шардирования. |
| 5. Высокоуровневая схема | 10 мин | Сервисы, хранилища, очереди, кэши. Пройти по схеме основной сценарий. |
| 6. Углубление | 15 мин | Узкие места, отказы, масштабирование, консистентность. Обычно интервьюер сам ведёт сюда. |
| 7. Итог | 2–3 мин | Что бы улучшил, мониторинг, какие метрики и алерты. |

## Шпаргалка по числам

- 1 день ≈ 86 400 с ≈ **10⁵ с**. 1 млн запросов в день ≈ 12 RPS. Пик ≈ 2–5× от среднего.
- Задержки: L1 ~1 нс, RAM ~100 нс, SSD random read ~100 мкс, запрос в рамках ДЦ ~0.5 мс, между ДЦ — десятки мс.
- Один инстанс Postgres: тысячи–десятки тысяч простых запросов в секунду, Redis — ~100 тыс. операций в секунду на ядро.
- Kafka: сотни МБ/с на брокер.

## Распределённые паттерны — знать обязательно

- **Transactional outbox** — запись в БД и публикация события атомарно: событие пишется в таблицу `outbox` в той же транзакции, отдельный процесс (или CDC через Debezium) отправляет в Kafka. Даёт at-least-once → консьюмеры идемпотентны.
- **Inbox / дедупликация** — таблица обработанных `message_id` с уникальным ключом.
- **Saga** — длинная бизнес-транзакция через несколько сервисов с компенсирующими действиями. Оркестрация vs хореография.
- **Idempotency key** — клиент присылает ключ, сервер хранит результат первого запроса.
- **CQRS** — отдельные модели для записи и чтения (например, запись в Postgres, чтение из Elasticsearch / денормализованной витрины).
- **Consistent hashing** — шардирование и кэши с минимальным перемещением ключей при изменении числа узлов.
- **CAP / PACELC** — честно: при сетевом разделе выбираем между доступностью и консистентностью, а без раздела — между латентностью и консистентностью.
- **Leader election, кворумы** — на уровне «зачем etcd/ZooKeeper и что такое Raft».

## Кейсы для тренировки

Проговаривай вслух с таймером или попроси Claude провести интервью: «проведи system design: кейс 1».

### Кейс 1. Лента объявлений с фильтрами

Главная страница категории: фильтры (цена, город, параметры категории), сортировки (дата, цена), 10 млн активных объявлений, 50k RPS на чтение.

<details><summary>На что обратить внимание</summary>

- Postgres не вытянет произвольные комбинации фильтров → поисковый движок (Elasticsearch / OpenSearch / свой индекс).
- Синхронизация: объявление меняется в Postgres → outbox → Kafka → индексатор. Задержка индексации (секунды) — допустима? Обсудить.
- Пагинация: `search_after` / курсор, не глубокий offset.
- Кэш первых страниц популярных выборок, короткий TTL.
- Ранжирование, продвинутые объявления (платные услуги) — отдельный сервис, смешивание выдачи.
</details>

### Кейс 2. Мессенджер между покупателем и продавцом

Чаты 1-на-1 по объявлению, доставка в реальном времени, история, непрочитанные, push-уведомления. 20 млн DAU.

<details><summary>На что обратить внимание</summary>

- WebSocket-шлюзы (stateful) + реестр «пользователь → шлюз» (Redis) + шина событий между шлюзами.
- Хранение сообщений: ключ шардирования `chat_id`, упорядоченность внутри чата (sequence на чат), а не глобальные часы.
- Гарантии доставки: at-least-once + идемпотентность по `client_message_id`, ack от клиента.
- Пользователь офлайн → push через отдельный сервис уведомлений.
- Счётчики непрочитанных — денормализация, а не `COUNT(*)`.
- Антиспам и модерация — асинхронно.
</details>

### Кейс 3. Сервис платного продвижения объявлений

Пользователь покупает «поднятие в поиске» за деньги со своего кошелька. Нельзя списать деньги дважды и нельзя продвинуть без оплаты.

<details><summary>На что обратить внимание</summary>

- Деньги — строгая консистентность: кошелёк в Postgres, двойная запись (ledger: проводки, а не просто поле `balance`).
- Idempotency key на покупку. Уникальный ключ в БД как последняя линия защиты.
- Сага: списать → активировать услугу → (при ошибке) вернуть деньги. Outbox для событий.
- Интеграция с внешним платёжным шлюзом: статусы, webhooks, сверка (reconciliation).
- Что видит пользователь при частичном отказе.
</details>

### Кейс 4. Счётчик просмотров объявления

Показывать продавцу «просмотров всего / сегодня», 100k событий/с, допустима задержка в минуту и небольшая погрешность.

<details><summary>На что обратить внимание</summary>

- Не `UPDATE ads SET views = views + 1` на каждый просмотр — горячие строки, блокировки.
- События → Kafka → агрегатор (окна по минутам) → батчевые инкременты в хранилище / ClickHouse.
- Защита от накруток: дедупликация по пользователю/устройству за окно, HyperLogLog для уникальных.
- Чтение: кэш, eventual consistency.
</details>

### Кейс 5. Модерация объявлений

Каждое новое объявление проходит автоматические проверки (ML-модели, стоп-слова, дубли, фото), часть уходит ручным модераторам. 1 млн новых объявлений в день, SLA публикации — 5 минут.

<details><summary>На что обратить внимание</summary>

- Конвейер: событие «объявление создано» → параллельные проверки → агрегация решения. Оркестратор / workflow-движок (Temporal) vs хореография через Kafka.
- Ручная очередь: распределение задач между модераторами без двойного взятия (`SKIP LOCKED` / лизинг), приоритеты, SLA.
- Медленная ML-модель: таймауты, деградация (отправить в ручную очередь), backpressure.
- Повторная модерация при редактировании, аудит решений.
</details>

## Что ещё почитать

- Martin Kleppmann — «Designing Data-Intensive Applications» (главы 5–9 обязательно).
- Alex Xu — «System Design Interview», тома 1 и 2.
- Технические блоги крупных компаний на Хабре — как устроены их платформы, шардирование, PaaS, Kafka. Вопросы по реальным системам компании, куда идёшь, — хороший способ показать интерес на финальном этапе.
