# Задача: circuit breaker

```
          N ошибок подряд               прошёл OpenTimeout
Closed ─────────────────────▶ Open ───────────────────────▶ HalfOpen
  ▲                            ▲                               │
  │       пробный успех        │       пробная ошибка          │
  └────────────────────────────┴───────────────────────────────┘
```

```go
cb := New(failureThreshold, openTimeout, now)
err := cb.Execute(func() error { return client.Call() })
cb.State()
```

- **Closed**: вызовы проходят. Успех сбрасывает счётчик ошибок. `failureThreshold` ошибок **подряд** → Open.
- **Open**: `fn` не вызывается, сразу `ErrOpen`. По прошествии `openTimeout` → HalfOpen (лениво, при следующем вызове или `State()`).
- **HalfOpen**: пропускается **ровно один** пробный вызов, остальные одновременные получают `ErrOpen`.
  Успех → Closed, ошибка → снова Open с новым отсчётом таймаута.
- `Execute` возвращает ошибку `fn` как есть.
- Потокобезопасность. `fn` выполняется **без** удержания мьютекса.

Вопросы:

- Почему счётчик «N подряд» плох под большой нагрузкой? Что лучше? (доля ошибок в скользящем окне + минимальное число запросов)
- Какие ошибки должны «открывать» breaker? (таймауты и 5xx — да; 4xx и `context.Canceled` клиента — нет)
- Breaker на клиенте или на сервере? На инстанс зависимости или на весь сервис?
