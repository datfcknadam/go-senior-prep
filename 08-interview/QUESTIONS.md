# Банк вопросов

Тренировка: закрой ответ, ответь вслух за 1–2 минуты, затем сверься. Если ответ занял 10 секунд — тебя спросят «а глубже?», готовь продолжение.

## Go: язык

<details><summary>Чем отличаются слайс и массив? Что происходит при append?</summary>

Массив — значение фиксированной длины, копируется целиком. Слайс — заголовок `{ptr, len, cap}` над массивом.
`append` при `len < cap` пишет в тот же массив (видно всем, кто его разделяет), иначе выделяет новый (примерно ×2 для маленьких, ~×1.25 для больших) и копирует.
</details>

<details><summary>Как устроена map? Почему нельзя взять адрес элемента?</summary>

Хеш-таблица; с Go 1.24 — Swiss Tables (группы по 8 слотов с контрольными байтами, поиск по группе). При росте элементы перемещаются, поэтому адрес нестабилен.
Не потокобезопасна, порядок итерации случаен, не сжимается после удаления.
</details>

<details><summary>Что такое интерфейс внутри? Почему nil-указатель в интерфейсе ≠ nil?</summary>

`iface{itab, data}` / `eface{type, data}`. Интерфейс равен nil только если и тип, и данные nil. `(*T)(nil)`, положенный в интерфейс, даёт ненулевой тип.
</details>

<details><summary>Value vs pointer receiver — как выбирать?</summary>

Pointer: метод меняет состояние; структура большая; есть поля, которые нельзя копировать (`sync.Mutex`); для единообразия, если хоть один метод на указателе.
Value: маленькие неизменяемые типы (time.Time-подобные). Помнить про method set и реализацию интерфейсов.
</details>

<details><summary>Как работают дженерики в Go и есть ли у них цена?</summary>

GC shape stenciling: одна инстанциация на «форму» (все указатели — одна форма) + словарь с информацией о типе. Для указательных типов вызовы методов идут через словарь — может быть медленнее ручного кода и мешать инлайнингу.
</details>

<details><summary>Что такое escape analysis? Как посмотреть?</summary>

Компилятор решает, может ли переменная жить на стеке. Если ссылка на неё переживает функцию (возврат указателя, сохранение в куче, интерфейс, замыкание) — в кучу. `go build -gcflags=-m`.
</details>

## Go: конкурентность и рантайм

<details><summary>Расскажи про модель GMP.</summary>

G — горутина, M — поток ОС, P — контекст планирования с локальной очередью (их GOMAXPROCS). M выполняет G только имея P. Work stealing между P, глобальная очередь,
handoff P при блокирующем syscall, netpoller для сетевого IO, асинхронное вытеснение сигналами с 1.14.
</details>

<details><summary>Как устроен канал? Что будет при записи в закрытый канал?</summary>

`hchan`: кольцевой буфер, мьютекс, очереди `recvq`/`sendq` ждущих горутин. Если есть ждущий получатель — значение копируется ему напрямую. Запись в закрытый — panic; чтение — нулевое значение и `ok=false`.
</details>

<details><summary>Как найти и предотвратить утечку горутин?</summary>

Симптом — растущий `runtime.NumGoroutine` / метрика. Поиск — `pprof/goroutine?debug=2`, группировка одинаковых стеков. В тестах — `goleak`.
Профилактика: у каждой горутины есть выход по `ctx.Done()`, отправки в каналы под `select` с отменой, владелец горутины ждёт её завершения.
</details>

<details><summary>Mutex vs RWMutex vs atomic vs канал — когда что?</summary>

Канал — передача владения данными и сигналы. Mutex — защита общего состояния. RWMutex — если чтений сильно больше и секция заметная (иначе дороже Mutex из-за накладных расходов).
atomic — одиночные счётчики и флаги, copy-on-write конфигурации через `atomic.Pointer`.
</details>

<details><summary>Как работает GC? Как уменьшить его влияние?</summary>

Конкурентный трёхцветный mark & sweep, write barrier, короткие STW. Триггер — `GOGC` (рост кучи на 100%), `GOMEMLIMIT` — мягкий лимит.
Уменьшить: меньше аллокаций (предвыделение, `sync.Pool`, меньше указателей в больших структурах), правильный `GOMEMLIMIT`.
</details>

<details><summary>Что такое data race и race condition? Это одно и то же?</summary>

Data race — одновременный доступ к памяти, хотя бы один на запись, без синхронизации; ловит `-race`. Race condition — логическая ошибка из-за порядка событий
(check-then-act), может быть и без data race, например в базе данных. Детектор её не найдёт.
</details>

<details><summary>Как сделать graceful shutdown HTTP-сервиса?</summary>

`signal.NotifyContext(SIGTERM)` → readiness отдаёт fail (перестаём получать трафик, ждём, пока балансировщик заметит) → `srv.Shutdown(ctx с таймаутом)` → остановить консьюмеры и воркеры, дождаться их → закрыть пулы БД, flush логов и метрик.
`terminationGracePeriodSeconds` в Kubernetes должен быть больше суммы этих таймаутов.
</details>

## Архитектура и практика

<details><summary>Как ты структурируешь Go-сервис?</summary>

Слои: транспорт (HTTP/gRPC handlers) → сервис (бизнес-логика) → репозитории/клиенты. Интерфейсы у потребителя, зависимости через конструкторы, `cmd/` + `internal/`.
Без фанатизма: не тащить «чистую архитектуру» с десятью слоями в маленький сервис.
</details>

<details><summary>Как тестируешь сервис?</summary>

Юнит-тесты бизнес-логики с фейками (табличные). Интеграционные с настоящей БД в testcontainers. Контрактные тесты между сервисами.
Тестируемое время (инъекция `now`). `-race` в CI. Не мокать то, чем не владеешь, — оборачивать.
</details>

<details><summary>Что такое observability? Что ты добавишь в новый сервис первым делом?</summary>

Метрики (RED: rate, errors, duration по эндпоинтам и зависимостям; USE для ресурсов), структурированные логи с trace id, распределённая трассировка (OpenTelemetry).
SLO и алерты по симптомам (error rate, latency p99), а не по причинам (CPU).
</details>

<details><summary>gRPC vs REST — когда что?</summary>

gRPC: межсервисное взаимодействие, строгий контракт (protobuf), стриминг, кодогенерация, HTTP/2. REST/JSON: публичные API, браузеры, простота отладки.
Обсудить: балансировка gRPC (долгие соединения → L7-балансировка или клиентская), deadline propagation.
</details>

<details><summary>Как обеспечить exactly-once обработку сообщений из Kafka?</summary>

Честный ответ: доставка — at-least-once, а «exactly-once» достигается **идемпотентной обработкой**: дедупликация по id сообщения в той же транзакции, что и бизнес-изменение (inbox),
или идемпотентные операции (upsert). Kafka transactions дают EOS только для цепочки read-process-write внутри Kafka.
</details>

<details><summary>Как ты подходишь к большой миграции / рефакторингу в продакшене?</summary>

Strangler fig, фичефлаги, теневой трафик (dual run + сравнение ответов), постепенная раскатка по процентам, метрики сравнения, возможность отката на каждом шаге.
</details>
