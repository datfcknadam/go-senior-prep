# Глава 14. Память и сборщик мусора

## Зачем

Латентность высоконагруженного сервиса на Go чаще всего упирается в аллокации и GC. Senior должен объяснить, где живёт переменная,
как устроены аллокатор и GC, почему они такие, и уметь настроить `GOGC`/`GOMEMLIMIT` под контейнер.

---

## 1. Стек и куча 🟢

- **Стек горутины:** аллокация — сдвиг указателя, освобождение — бесплатно при выходе из функции, GC не участвует.
- **Куча:** нужны аллокатор и GC, память разделяема между горутинами.
- Где жить переменной, решает **компилятор** (escape analysis), а не способ создания: `new(T)` и `&T{}` могут оказаться на стеке,
  а локальная переменная — в куче.

## 2. Escape analysis 🟡

Объект остаётся на стеке, если компилятор **доказал**, что тот не переживёт кадр функции и его размер известен. Объект убегает в кучу, когда:

- возвращается указатель на него;
- он сохраняется в глобальную переменную, поле объекта из кучи, канал или интерфейс, который убегает;
- его захватывает убегающее замыкание (например, `go func()`);
- размер неизвестен при компиляции (`make([]T, n)` с переменным `n`; с 1.25 маленькие такие слайсы тоже могут жить на стеке) или слишком велик;
- он передаётся в функцию, которую анализ не видит насквозь (вызов через интерфейс или func-значение) — компилятор консервативен.

```bash
go build -gcflags='-m' ./...        # решения: escapes to heap, moved to heap, does not escape
go build -gcflags='-m -m' ./...     # с причинами
```

**Инлайнинг усиливает escape analysis:** после инлайна конструктора `NewX()` объект часто остаётся на стеке вызывающего.
Бюджет инлайна около 80 узлов AST; PGO поднимает его для горячих функций.

## 3. Аллокатор 🔴

Требования: очень быстрая аллокация мелочи, без глобальных локов на многих ядрах, низкая фрагментация при **неперемещающем** GC.
Ответ — схема по мотивам **TCMalloc**: классы размеров и многоуровневые кеши.

```
mcache (на каждый P, без локов)
   └── текущий span на каждый size class (отдельно scan и noscan)
mcentral (на каждый size class, с локом)
   └── span'ы со свободными слотами и без
mheap (глобальный, с локом)
   └── страницы по 8 КБ, арены по 64 МБ у ОС
```

- **Span** — блок страниц, нарезанный на объекты **одного** размера. Свободные слоты — битовая карта, аллокация — поиск следующего нулевого бита.
- **~68 size classes** (8, 16, 24, 32, 48, 64, … 32 КБ). Запрос округляется вверх до класса, потери ≤ 12,5%. Отсюда «странный» cap слайсов (глава 4).
- **scan / noscan:** объекты **без указателей** лежат в отдельных span'ах, и GC их не сканирует вовсе. Поэтому `[]int` дешевле для GC, чем `[]*int`.
- Три пути: **tiny** (< 16 Б без указателей, пакуются вместе), **small** (≤ 32 КБ: mcache → mcentral → mheap), **large** (> 32 КБ, напрямую из mheap под локом).
- Память возвращается ОС фоновым **scavenger**'ом, поэтому RSS падает не сразу после GC.

## 4. Сборщик мусора 🟡

### Решения и их причины

| Решение | Почему |
|---|---|
| **конкурентный** mark & sweep | приоритет — низкая латентность серверов; маркировка идёт параллельно с программой, паузы STW короткие |
| **неперемещающий** | указатели уходят в cgo и unsafe, интерьерные указатели (`&s.field`) усложняют перемещение; size classes дают приемлемую фрагментацию |
| **без поколений** | escape analysis уже держит многие короткоживущие объекты на стеке; generational GC требует write barrier всегда, а не только во время GC |
| **трёхцветный** | позволяет маркировать инкрементально с понятным инвариантом |

### Трёхцветная маркировка 🔴

- **Белый** — не достигнут (кандидат на удаление), **серый** — достигнут, поля не просканированы, **чёрный** — достигнут и просканирован.
- Корни (стеки, глобальные переменные) красятся в серый. Берём серый, его ссылки красим в серый, сам объект — в чёрный. Повторяем, пока серых нет. Белые — мусор.
- **Проблема:** программа может записать указатель на белый объект в чёрный и удалить его из серого. Объект жив, но останется белым и будет освобождён.
- **Write barrier:** во время маркировки каждая запись указателя в кучу идёт через барьер. Go использует **гибридный барьер** (1.8+):
  красит и старое значение (Юаса), и новое (Дейкстра). Благодаря этому не нужен перескан всех стеков под STW в конце маркировки,
  и паузы упали с десятков миллисекунд до < 1 мс.
- Объекты, созданные во время маркировки, сразу чёрные.

### Фазы цикла

1. **Sweep termination** (STW, короткий): включается write barrier.
2. **Mark** (конкурентно): фоновые воркеры GC занимают **25% CPU**.
3. **Mark termination** (STW, короткий): барьер выключается.
4. **Sweep** (конкурентно и лениво): span'ы подметаются фоном или при следующей аллокации из них.

### Когда запускается GC 🟡

- **GOGC=100** (по умолчанию): следующий цикл начнётся, когда куча дорастёт до `live_heap × (1 + GOGC/100)`. Живые 1 ГБ → следующий GC при ~2 ГБ.
  Больше GOGC — реже GC и больше памяти; меньше — наоборот.
- **Pacer** заранее решает, когда начать маркировку, чтобы закончить её к целевому размеру.
- **Mark assist:** если горутина аллоцирует быстрее, чем GC маркирует, её заставляют помогать маркировать прямо в `mallocgc`.
  Для сервиса это выглядит как **всплески латентности у запросов, которые активно аллоцируют**.
- **GOMEMLIMIT** (1.19+): мягкий лимит общей памяти. При приближении к нему GC запускается чаще, независимо от GOGC.
  Типичная настройка — ~90% лимита контейнера: экономно, но без OOMKill.
  Опасность — **death spiral**, когда живых данных почти столько же, сколько лимит, и GC работает непрерывно. Поэтому GC ограничен ~50% CPU,
  после чего лимит пробивается, а не процесс зависает.
- `GOGC=off` + `GOMEMLIMIT` — режим «копи до лимита», подходит для batch-задач.

### Green Tea GC (1.25 эксперимент, 1.26 по умолчанию) 🔴

Классическая маркировка прыгает по объектам в случайном порядке и упирается в задержки памяти. Green Tea сканирует **страницами (span'ами)**:
в очередь кладётся страница, и её объекты сканируются пачкой. Лучше локальность кеша, возможна векторизация. Время GC меньше на 10–40% в типичных нагрузках.

## 5. Финализаторы, cleanup, weak 🔴

- `runtime.SetFinalizer` задерживает освобождение на цикл, запуск не гарантирован, циклы с финализаторами не собираются.
- `runtime.AddCleanup` (1.24) — замена получше: не воскрешает объект, допускает несколько cleanup'ов.
- `weak.Pointer[T]` (1.24) — слабые ссылки для кешей и канонизации. `unique.Make` (1.23) — интернирование значений.

## 6. Как это влияет на код сервиса 🟡

- **Меньше аллокаций на запрос** → реже GC → меньше mark assist → стабильнее p99. Меряй `allocs/op` и heap-профилем (глава 15).
- Приёмы: предвыделение (`make(..., 0, n)`, `Grow`), `sync.Pool` для буферов, без `[]byte ↔ string` в горячем пути, без упаковки мелочи в `any`,
  `strconv.AppendInt` вместо `fmt.Sprintf`.
- **Меньше указателей — меньше работы GC:** `[]T` вместо `[]*T`, индексы вместо указателей, id вместо строковых ключей.
- **Большие кеши в памяти:** миллионы объектов с указателями дают долгую маркировку. Решения: данные без указателей, шардирование,
  off-heap-подход (bigcache и freecache хранят всё в больших `[]byte`), `GOMEMLIMIT`.
- **Контейнер:** memory limit → `GOMEMLIMIT`. Без этого получаются «необъяснимые» OOMKill при всплеске.

## 7. Наблюдение 🟡

```bash
GODEBUG=gctrace=1 ./app
# gc 12 @3.4s 2%: 0.02+1.3+0.03 ms clock, ... 120->125->60 MB, 121 MB goal, 8 P
#   STW1 + конкурентная маркировка + STW2; куча до → после маркировки → живая; цель
```

Метрики `runtime/metrics`: `/gc/pauses:seconds`, `/gc/heap/goal:bytes`, `/cpu/classes/gc/...`. В Prometheus — `go_gc_duration_seconds`, `go_memstats_*`.

## Ловушки

- «Переменная создана через `new`, значит в куче» — нет, решает escape analysis.
- `GOMEMLIMIT` равен лимиту контейнера: не остаётся запаса на не-кучу (стеки, рантайм, cgo).
- Кеш на `map[string]*Item` на миллионы элементов, и CPU уходит в GC.
- Оптимизация аллокаций без профиля.

## Закрепление

Упражнения запускаются прямо в панели (`make panel`, эта глава): правь код в редакторе и жми ▶ или <kbd>⌘/Ctrl+Enter</kbd>. Упражнение засчитывается, когда вывод совпал с ожидаемым; конкурентные прогоняются с `-race`. Подсказки открываются по одной — сначала попробуй без них.

```go
// exercise: Ноль аллокаций
// expect: words: 5
// expect: allocs: 0
// hint: strings.Fields строит слайс строк — это аллокация. А чтобы посчитать слова, слайс не нужен.
// hint: Пройди по рунам и считай переходы «пробел → не пробел» (unicode.IsSpace). Проверь кнопкой escape, что ничего не уходит в кучу.
package main

import (
	"fmt"
	"strings"
	"testing"
)

func countWords(s string) int {
	return len(strings.Fields(s))
}

func main() {
	s := "  Продам   велосипед почти новый  торг "
	fmt.Println("words:", countWords(s))
	fmt.Println("allocs:", testing.AllocsPerRun(100, func() { countWords(s) }))
}
```

```go
// exercise: Утечка через подслайс
// expect: kept: 100
// expect: heap < 10 MB: true
// hint: packet[:16] — это заголовок слайса, указывающий на весь мегабайтный массив. Пока жив подслайс, жив и массив.
// hint: Скопируй нужные байты в новый маленький слайс: bytes.Clone(packet[:16]) или make + copy.
package main

import (
	"fmt"
	"runtime"
)

// header возвращает первые 16 байт пакета.
func header(packet []byte) []byte {
	return packet[:16]
}

func main() {
	var kept [][]byte
	for range 100 {
		packet := make([]byte, 1<<20) // 1 МБ из сети
		kept = append(kept, header(packet))
	}
	runtime.GC()
	var ms runtime.MemStats
	runtime.ReadMemStats(&ms)
	fmt.Println("kept:", len(kept))
	fmt.Println("heap < 10 MB:", ms.HeapAlloc < 10<<20)
	runtime.KeepAlive(kept)
}
```
