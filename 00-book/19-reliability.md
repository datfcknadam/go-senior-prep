# Глава 19. Надёжность

## Зачем

В системе из сотен микросервисов любой сетевой вызов может упасть, зависнуть или ответить медленно. Senior должен объяснить,
как его сервис ведёт себя при отказе зависимостей, и не превратить частичный отказ в каскадный. Это постоянная тема system design
и вопросов «а что будет, если…».

---

## 1. Таймауты 🟢

- Таймаут на **каждый** сетевой вызов. `http.Client{}` без `Timeout` ждёт вечно, и горутины копятся до OOM.
- Дедлайн передаётся через `context` по всей цепочке, а между сервисами — через gRPC deadline propagation или заголовок.
- **Бюджет:** если у входящего запроса SLA 300 мс, нет смысла ставить 1 с на вызов зависимости. Таймаут зависимости ≈ её p99 с запасом,
  но меньше оставшегося бюджета.
- Таймауты на уровне сервера (глава 16) и базы (`statement_timeout`) тоже обязательны.

## 2. Retry 🟢

```go
func Do(ctx context.Context, attempts int, fn func(ctx context.Context) error) error {
    var err error
    for i := range attempts {
        if err = fn(ctx); err == nil || !retryable(err) {
            return err
        }
        if i == attempts-1 {
            break
        }
        backoff := min(50*time.Millisecond<<i, 2*time.Second)
        sleep := rand.N(backoff) // full jitter, math/rand/v2
        t := time.NewTimer(sleep)
        select {
        case <-t.C:
        case <-ctx.Done():
            t.Stop()
            return errors.Join(err, ctx.Err())
        }
    }
    return err
}
```

- Повторять только **идемпотентные** операции и только **временные** ошибки: таймаут, 503, 429, connection reset, serialization failure.
  Не повторять 400, 404, ошибки валидации — результат не изменится.
- **Exponential backoff с jitter.** Без jitter все клиенты ретраят синхронно и добивают восстанавливающийся сервис волнами.
- **Retry storm:** 3 уровня сервисов × 3 попытки = 27× нагрузки на нижний уровень. Ретраят **на одном уровне** стека и ограничивают долю ретраев
  (retry budget, например ≤ 10% трафика).
- Учитывай `Retry-After` в ответах 429/503.
- Ожидание между попытками — в select с `ctx.Done()`, а не `time.Sleep`.

## 3. Идемпотентность 🟢

Ретраи и at-least-once доставка безопасны, только если повтор не меняет результат.

- **Idempotency-Key:** клиент генерирует ключ на операцию и присылает его в заголовке. Сервер в той же транзакции, что и операция, сохраняет
  `(key, request_hash, response)` с уникальным ограничением. Повтор с тем же ключом возвращает сохранённый ответ, не выполняя операцию.
  Тот же ключ с другим телом — 422.
- **Уникальные ограничения в БД** — последняя линия защиты: `INSERT ... ON CONFLICT DO NOTHING`.
- **Дедупликация консьюмеров** — inbox-таблица обработанных `message_id` (глава 18).
- Естественно идемпотентные операции: `SET status = 'paid'` идемпотентна, а `balance = balance - 100` — нет.

## 4. Circuit breaker 🟡

Если зависимость лежит, бесполезно продолжать слать ей запросы и ждать таймаутов: это тратит горутины и соединения и мешает ей подняться.

```
Closed ──(доля ошибок > порога за окно)──► Open ──(таймаут)──► Half-Open
  ▲                                         ▲                    │
  └──────────(пробные успешны)──────────────┼────────────────────┘
                                            └──(пробный упал)────┘
```

- **Closed:** запросы идут, ошибки считаются в скользящем окне. **Open:** запросы сразу получают ошибку, без похода в сеть.
  **Half-Open:** пропускается ограниченное число пробных запросов, по их результату — назад в Closed или снова в Open.
- Считать ошибками нужно сбои зависимости (таймауты, 5xx), а не 4xx клиента.
- Брейкер — на каждую зависимость (и иногда на каждый эндпоинт), не один на всё.
- Библиотека: `sony/gobreaker`.

## 5. Деградация и fallback 🟡

Что отдать, когда зависимость недоступна:
- кешированное (возможно, устаревшее) значение;
- значение по умолчанию;
- **урезанный ответ:** страница объявления без блока «похожие объявления» лучше, чем ошибка 500.

Критичные и некритичные зависимости разделяют заранее: падение рекомендаций не должно ронять карточку объявления.

## 6. Ограничение нагрузки 🟡

- **Rate limiting** (глава 12) — защита от отдельных клиентов: по пользователю, IP, API-ключу. Ответ 429 с `Retry-After`.
- **Load shedding** — защита сервиса от перегрузки целиком: если очередь или конкурентность выше порога, отвечать 503 **быстро**.
  Быстрый отказ лучше медленного: медленный держит ресурсы и тянет за собой вызывающих.
- **Ограничение конкурентности** на входе (семафор на число одновременно обрабатываемых запросов) и на каждую зависимость.
- **Bulkhead** — изоляция ресурсов: отдельные пулы горутин и соединений под разные зависимости, чтобы одна медленная не съела всё.
- **Backpressure** — медленный потребитель замедляет производителя (ограниченные буферы, ожидание), а не копит бесконечную очередь в памяти.

## 7. Hedged requests и прочее 🔴

- **Hedged request:** если ответ не пришёл за p95, отправить дубль в другую реплику и взять первый ответ. Срезает хвосты латентности
  ценой нескольких процентов лишней нагрузки. Только для идемпотентных чтений.
- **Graceful degradation при старте:** не падать, если некритичная зависимость недоступна при старте; ретраить подключение в фоне.
- **Timeouts + retries + circuit breaker** работают вместе: таймаут превращает зависание в ошибку, ретрай лечит единичный сбой, брейкер останавливает ретраи при массовом.

## 8. Распределённые блокировки и согласованность 🔴

- Распределённый лок (Redis `SET NX PX`, etcd, advisory lock в Postgres) **не гарантирует** взаимного исключения при паузах GC и сетевых задержках:
  владелец может думать, что держит лок, когда тот уже истёк. Защита — **fencing token** (монотонный номер, который проверяет хранилище).
- Где возможно, вместо распределённого лока используй атомарные операции в БД: условный `UPDATE`, уникальные ограничения, `SELECT FOR UPDATE SKIP LOCKED`.
- Почему Redlock спорный — разбор Мартина Клеппманна «How to do distributed locking».

## Ловушки

- Ретраи неидемпотентных операций (двойное списание).
- Ретраи на каждом уровне стека.
- Backoff без jitter.
- Один circuit breaker на все зависимости.
- Liveness-проба зависит от базы: падение базы перезапускает все поды, и становится только хуже.
- Бесконечная очередь в памяти вместо отказа.
- Распределённый лок как гарантия корректности без fencing.

## Закрепление

Упражнения запускаются прямо в панели (`make panel`, эта глава): правь код в редакторе и жми ▶ или <kbd>⌘/Ctrl+Enter</kbd>. Упражнение засчитывается, когда вывод совпал с ожидаемым; конкурентные прогоняются с `-race`. Подсказки открываются по одной — сначала попробуй без них.

```go
// exercise: Идемпотентный платёж
// expect: charges: 1
// expect: same response: true
// flags: race
// hint: Мало сохранить ответ после списания: 20 параллельных запросов придут раньше, чем первый закончит. Нужна запись «в процессе».
// hint: map[key]*call, где call хранит done chan struct{} и resp. Первый создаёт call и работает, остальные ждут <-c.done (как singleflight, но ответ хранится).
package main

import (
	"fmt"
	"sync"
	"time"
)

type Payments struct {
	mu      sync.Mutex
	charges int
}

// Pay списывает деньги ровно один раз на ключ идемпотентности. Повтор с тем же ключом —
// в том числе параллельный — возвращает сохранённый ответ.
func (p *Payments) Pay(key string, amount int) string {
	p.mu.Lock()
	p.charges++
	n := p.charges
	p.mu.Unlock()
	time.Sleep(10 * time.Millisecond) // поход в банк
	return fmt.Sprintf("payment-%d", n)
}

func main() {
	p := &Payments{}
	resp := make([]string, 20)
	var wg sync.WaitGroup
	for i := range resp {
		wg.Add(1)
		go func() {
			defer wg.Done()
			resp[i] = p.Pay("order-42", 100) // клиент ретраит по таймауту
		}()
	}
	wg.Wait()

	same := true
	for _, r := range resp {
		same = same && r == resp[0]
	}
	fmt.Println("charges:", p.charges)
	fmt.Println("same response:", same)
}
```

```go
// exercise: Сброс нагрузки
// expect: accepted: 3
// expect: rejected: 7
// flags: race
// hint: Семафор на буферизованном канале: занять слот — отправка, освободить — чтение.
// hint: Неблокирующая попытка — select с default: select { case l.sem <- struct{}{}: return true; default: return false }.
package main

import (
	"fmt"
	"sync"
	"sync/atomic"
)

type Limiter struct{ sem chan struct{} }

func NewLimiter(n int) *Limiter { panic("TODO") }

// TryAcquire не ждёт: false, если все слоты заняты. Лучше быстро ответить 429/503, чем копить очередь.
func (l *Limiter) TryAcquire() bool { panic("TODO") }
func (l *Limiter) Release()         { panic("TODO") }

func main() {
	l := NewLimiter(3)
	release := make(chan struct{})
	var accepted, rejected atomic.Int32
	var tried, done sync.WaitGroup
	for range 10 {
		tried.Add(1)
		done.Add(1)
		go func() {
			defer done.Done()
			if !l.TryAcquire() {
				rejected.Add(1)
				tried.Done()
				return
			}
			accepted.Add(1)
			tried.Done()
			<-release // обрабатываем запрос
			l.Release()
		}()
	}
	tried.Wait()
	close(release)
	done.Wait()
	fmt.Println("accepted:", accepted.Load())
	fmt.Println("rejected:", rejected.Load())
}
```
