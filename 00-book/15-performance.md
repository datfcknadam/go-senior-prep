# Глава 15. Профилирование и оптимизация

## Зачем

На senior-интервью почти всегда просят: «расскажи, как ты нашёл и починил проблему с производительностью». Ждут не список флагов,
а метод: симптом → метрики → профиль → гипотеза → фикс → результат в цифрах. Эта глава даёт инструменты и метод.

---

## 1. Метод 🟢

1. **Сформулируй симптом в метрике:** «p99 `/feed` вырос с 80 до 400 мс после релиза», а не «тормозит».
2. **Определи ресурс:** CPU, память и GC, ожидание (БД, лок, сеть), планировщик.
3. **Сними профиль** нужного вида (таблица ниже). В проде, а не на ноутбуке, если возможно.
4. **Гипотеза → минимальный фикс → бенчмарк** до и после через `benchstat`.
5. **Проверь эффект в проде** той же метрикой.

Не оптимизируй без профиля. Интуиция о том, где узкое место, ошибается чаще, чем кажется.

## 2. pprof 🟢

```go
import _ "net/http/pprof" // регистрирует /debug/pprof/* в http.DefaultServeMux

go func() { _ = http.ListenAndServe("localhost:6060", nil) }() // ОТДЕЛЬНЫЙ внутренний порт
```

```bash
go tool pprof -http=:8081 'http://localhost:6060/debug/pprof/profile?seconds=30'  # CPU
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap                   # память
curl 'localhost:6060/debug/pprof/goroutine?debug=2' > g.txt                        # стеки всех горутин
go test -bench . -benchmem -cpuprofile cpu.out -memprofile mem.out                 # из бенчмарка
```

### Какой профиль на какой вопрос

| Вопрос | Профиль | Как читать |
|---|---|---|
| на что уходит CPU | `profile?seconds=30` | семплирование 100 Гц; flame graph, `top -cum` |
| кто аллоцирует (давление на GC) | `heap`, `-sample_index=alloc_space` | суммарно за время жизни процесса |
| кто держит память сейчас | `heap`, `inuse_space` | живое на момент последнего GC |
| утечка горутин | `goroutine?debug=2` | «N горутин в одном и том же месте» + время ожидания |
| где ждут локи | `mutex` (включить `runtime.SetMutexProfileFraction`) | время, которое другие ждали из-за этого Unlock |
| где блокируются | `block` (включить `runtime.SetBlockProfileRate`) | каналы, select, мьютексы |
| латентность, а не CPU | `trace` | планирование, GC, syscall, сеть на шкале времени |

- **CPU-профиль показывает только on-CPU время.** Если запрос медленный из-за ожидания, CPU-профиль будет «чистым». Смотри block, mutex и trace.
- В веб-интерфейсе pprof: **Flame Graph** (ширина = доля времени), **Top** (`flat` — в самой функции, `cum` — вместе с вызванными), **Source** с построчной разметкой.
- **Continuous profiling** (Pyroscope, Parca, Grafana Profiles) в проде — стандарт для высоконагруженных сервисов: профиль уже есть, когда случился инцидент.

## 3. go tool trace 🟡

```bash
curl -o trace.out 'localhost:6060/debug/pprof/trace?seconds=5'
go tool trace trace.out
```

Показывает каждую горутину на шкале времени: когда она была runnable, но не выполнялась, когда ждала сеть или syscall, когда работал GC и mark assist.
Отвечает на вопрос «почему этот запрос шёл 50 мс, если CPU он потратил 2 мс». С 1.25 есть **flight recorder** (`runtime/trace.FlightRecorder`):
трасса последних секунд в кольцевом буфере, которую сохраняют при аномалии.

## 4. Бенчмарки 🟢

Основы в главе 9. Правила честного сравнения:
- `-count=10` и `benchstat old.txt new.txt`, а не один прогон.
- Стабильная машина: без турбобуста и фоновых задач, лучше одна и та же.
- `-benchmem`: в горячем пути аллокации важнее наносекунд.
- `b.Loop()` (1.24) вместо `for i := 0; i < b.N; i++`: компилятор не выбросит вычисление, подготовка не попадёт в замер.
- Бенчмарк на реалистичных данных: размер входа сильно меняет картину (кеш процессора, рост слайсов).

## 5. PGO 🟡

Profile-guided optimization: CPU-профиль из прода, положенный как `default.pgo` в каталог main-пакета, используется при сборке автоматически.
Компилятор агрессивнее инлайнит горячие функции и **девиртуализирует** горячие вызовы через интерфейс (проверка типа + прямой вызов).
Обычно это 2–14% CPU. Профиль нужно периодически обновлять.

## 6. Частые оптимизации 🟡

| Проблема | Решение |
|---|---|
| рост слайса или мапы в цикле | `make(..., 0, n)`, `make(map, n)` |
| конкатенация строк | `strings.Builder` + `Grow`, `strconv.Append*` вместо `fmt.Sprintf` |
| `[]byte ↔ string` в горячем пути | работать в одном представлении; `unsafe.String` только при доказанной неизменяемости |
| временные буферы | `sync.Pool` |
| упаковка в `any` (логирование, `fmt`) | типизированные поля `slog.Int`, `slog.String`; не логировать в горячем цикле |
| `encoding/json` на рефлексии | кодогенерация (easyjson), `json/v2` (1.25, `GOEXPERIMENT=jsonv2`), меньше полей |
| один глобальный мьютекс | шардирование, атомики, copy-on-write через `atomic.Pointer` |
| много мелких запросов к БД | батчинг, `COPY`, кеш |
| много указателей в большом кеше | структуры без указателей, off-heap |
| регулярки в цикле | компилировать один раз; часто хватает `strings` |

## 7. Типичные истории «нашёл и починил» 🟡

| Симптом | Причина | Как нашли | Фикс |
|---|---|---|---|
| память растёт, OOMKill | утечка горутин | `go_goroutines` растёт, `goroutine?debug=2` — тысячи в одной строке | select с `ctx.Done()`, буфер 1 у канала результата |
| память растёт | подслайс большого буфера в кеше | heap `inuse_space` | `bytes.Clone` |
| p99 скачет | частый GC из-за аллокаций | `gctrace`, heap `alloc_space`, mark assist в trace | пулы, предвыделение, `GOMEMLIMIT` |
| CPU в потолке, троттлинг | GOMAXPROCS больше лимита в контейнере | метрика `container_cpu_cfs_throttled` | Go 1.25+ или automaxprocs |
| запросы ждут, CPU низкий | глобальный мьютекс | mutex-профиль | шардирование |
| медленный ответ, CPU низкий | пул соединений к БД исчерпан | `db.Stats().WaitCount`, block-профиль | размер пула, таймауты, короче транзакции |
| много CPU в JSON | рефлексия | CPU-профиль | кодогенерация |

Подготовь **1–2 собственные истории** по этой схеме с конкретными цифрами «до» и «после». Это один из самых ценных ответов на интервью.

## Ловушки

- Оптимизация без профиля и без бенчмарка.
- pprof на публичном порту.
- Вывод по CPU-профилю, когда проблема в ожидании.
- Сравнение бенчмарков по одному прогону.
- Микрооптимизация, ухудшившая читаемость, ради 2% в негорячем коде.

## Закрепление

Упражнения запускаются прямо в панели (`make panel`, эта глава): правь код в редакторе и жми ▶ или <kbd>⌘/Ctrl+Enter</kbd>. Упражнение засчитывается, когда вывод совпал с ожидаемым; конкурентные прогоняются с `-race`. Подсказки открываются по одной — сначала попробуй без них.

```go
// exercise: Предаллокация
// expect: len: 1000
// expect: allocs: 1
// hint: append в nil-слайс растит массив ступенями: каждая ступень — новая аллокация и копирование.
// hint: Размер известен заранее: make([]int, 0, len(ads)) — ровно одна аллокация.
package main

import (
	"fmt"
	"testing"
)

type Ad struct {
	ID    int
	Title string
}

func collectIDs(ads []Ad) []int {
	var ids []int
	for _, a := range ads {
		ids = append(ids, a.ID)
	}
	return ids
}

func main() {
	ads := make([]Ad, 1000)
	for i := range ads {
		ads[i].ID = i + 1
	}
	fmt.Println("len:", len(collectIDs(ads)))
	fmt.Println("allocs:", testing.AllocsPerRun(100, func() { collectIDs(ads) }))
}
```

```go
// exercise: Сборка строки
// expect: 1,2,3,4,5 ... 998,999,1000
// expect: allocs: 1
// hint: s += ... на каждой итерации создаёт новую строку, fmt.Sprintf ещё и упаковывает аргументы в интерфейсы.
// hint: strings.Builder + Grow(оценка размера) — одна аллокация. Числа пиши через strconv.AppendInt в буфер на стеке: var tmp [20]byte.
package main

import (
	"fmt"
	"testing"
)

// join склеивает id через запятую.
func join(ids []int) string {
	s := ""
	for i, id := range ids {
		if i > 0 {
			s += ","
		}
		s += fmt.Sprintf("%d", id)
	}
	return s
}

func main() {
	ids := make([]int, 1000)
	for i := range ids {
		ids[i] = i + 1
	}
	s := join(ids)
	fmt.Println(s[:9], "...", s[len(s)-12:])
	fmt.Println("allocs:", testing.AllocsPerRun(100, func() { join(ids) }))
}
```
