# Глава 13. Планировщик GMP

## Зачем

«Как работает планировщик Go» — обязательный вопрос senior-интервью. Хороший ответ объясняет не только модель G/M/P,
но и **почему** она такая, и как это влияет на сервис: syscall'ы, сетевой IO, GOMAXPROCS в контейнере, хвосты латентности.

---

## 1. Зачем свой планировщик 🟡

Потоки ОС дорогие: стек 1–8 МБ, переключение через ядро занимает микросекунды, а ядро не знает, что горутина ждёт канал.
Планировщик в user space переключает горутины примерно за 100 нс и понимает семантику Go: каналы, мьютексы, сетевые ожидания.
Это модель **M:N** — N горутин на M потоков.

## 2. Три сущности 🟡

| | Что это | Сколько |
|---|---|---|
| **G** | горутина: стек, регистры, статус | сколько угодно |
| **M** | поток ОС, который исполняет код | растёт по необходимости (лимит 10 000) |
| **P** | «право исполнять Go-код» + локальные ресурсы | ровно `GOMAXPROCS` |

**Почему три, а не две.** До Go 1.1 были только G и M с **одной глобальной очередью под мьютексом**, и на многих ядрах всё упиралось в этот лок.
P добавили, чтобы у каждого исполнителя были свои ресурсы без локов:
- локальная очередь горутин (кольцо на 256) + слот `runnext`;
- `mcache` — кеш аллокатора (глава 14);
- буферы работы GC, пул `_defer`, таймеры.

Потоков может быть много (часть стоит в syscall'ах), а P ровно `GOMAXPROCS`. Так параллелизм Go-кода ограничен числом ядер,
а заблокированные потоки не отнимают слоты исполнения.

## 3. Где M ищет работу 🟡

`schedule()` → `findRunnable()`:

1. Раз в 61 тик — из **глобальной** очереди, чтобы она не голодала при загруженных локальных.
2. `runnext`, затем локальная очередь P.
3. Глобальная очередь.
4. **netpoll** без ожидания: горутины, у которых готовы сокеты.
5. **Work stealing:** до 4 проходов по случайным P, украсть **половину** их очереди. Плюс чужие таймеры.
6. Ничего нет — P уходит в idle, M засыпает.

- **`runnext`:** если горутина A отправила в канал и разбудила B, то B выполнится следующей на том же P. Данные ещё в кеше,
  а пара producer/consumer работает почти как вызов функции. Новая `go f()` тоже попадает в `runnext`.
- **Почему крадут половину:** одну — придётся красть снова очень скоро, всё — жертва останется без работы.
- **Spinning M:** поток, ищущий работу, некоторое время крутится, а не засыпает: разбудить спящий поток стоит микросекунды.
  Одновременно spinning-потоков не больше половины занятых P.

## 4. Блокировки: что происходит с потоком 🟡

| Ситуация | Что делает рантайм |
|---|---|
| канал, мьютекс, `Sleep`, select | G паркуется (`_Gwaiting`), M берёт следующую G. Поток **не** блокируется |
| сетевой IO | сокет неблокирующий; при `EAGAIN` G паркуется на **netpoller** (epoll/kqueue/IOCP), потом netpoll вернёт её в очередь |
| блокирующий syscall (файл, cgo) | M уходит в syscall вместе с G. **sysmon** через ~20 мкс видит застрявший P и делает **handoff**: отдаёт P другому M |
| возврат из syscall | M пытается вернуть свой P, иначе берёт свободный, иначе G идёт в глобальную очередь, а M засыпает |

Отсюда: **сетевой IO дешёвый** — горутина на соединение нормальна. А **файловый IO и cgo плодят потоки**, и параллелизм таких операций надо ограничивать.

## 5. sysmon и вытеснение 🔴

**sysmon** — отдельный поток без P. Он опрашивает netpoll, если его давно никто не опрашивал, отбирает P у syscall'ов, вытесняет горутины,
работающие дольше 10 мс, и форсирует GC, если его не было 2 минуты.

**Вытеснение:**
- **Кооперативное:** sysmon записывает в `g.stackguard0` значение `stackPreempt`. Пролог ближайшей функции проверяет стек,
  «думает», что он кончился, идёт в `morestack` и там уступает процессор. Проверка роста стека заодно служит точкой вытеснения.
- **Асинхронное (1.14+):** потоку посылается сигнал `SIGURG`. Обработчик проверяет, что горутина в безопасной точке, и подменяет PC на вызов уступки.
  Это лечит `for {}` без вызовов функций, который раньше мог повесить GC: STW ждал бы такую горутину вечно.

## 6. GOMAXPROCS в контейнерах 🟡

- Раньше `GOMAXPROCS` был равен числу ядер **ноды**. При CPU limit = 2 на 64-ядерной ноде получалось 64 активных потока: квота CFS выжигалась
  за первые миллисекунды периода (100 мс), и процесс **троттлился** до конца периода. Это прямо бьёт по p99.
- С **Go 1.25** рантайм читает cgroup-лимит CPU и периодически его перепроверяет. До 1.25 использовали `go.uber.org/automaxprocs`.
- Если задан только CPU request без limit, автоматики нет: GOMAXPROCS выставляют явно, исходя из нагрузки.

## 7. Наблюдение 🟡

```bash
GODEBUG=schedtrace=1000,scheddetail=1 ./app   # раз в секунду: очереди P, состояние M
curl -o trace.out 'localhost:6060/debug/pprof/trace?seconds=5' && go tool trace trace.out
```

`go tool trace` показывает, где горутина была runnable, но не выполнялась (задержка планировщика), где ждала сеть, syscall или GC.
Метрика `/sched/latencies:seconds` из `runtime/metrics` даёт распределение задержки планирования.

## Ловушки

- «Горутина = поток» или «горутины выполняются по очереди на одном потоке» — обе формулировки неверны.
- `runtime.Gosched()` и `runtime.LockOSThread()` в прикладном коде почти никогда не нужны.
- Неограниченное число параллельных файловых или cgo-операций: тысячи потоков ОС.
- `GOMAXPROCS` больше лимита CPU в контейнере на Go < 1.25.

## Закрепление

Упражнения запускаются прямо в панели (`make panel`, эта глава): правь код в редакторе и жми ▶ или <kbd>⌘/Ctrl+Enter</kbd>. Упражнение засчитывается, когда вывод совпал с ожидаемым; конкурентные прогоняются с `-race`. Подсказки открываются по одной — сначала попробуй без них.

```go
// exercise: CPU-bound по числу P
// expect: 1 worker: 17984
// expect: 7 workers: 17984
// expect: GOMAXPROCS workers: 17984
// flags: race
// hint: Для CPU-bound работы больше GOMAXPROCS горутин не ускоряет: одновременно на процессоре всё равно P штук.
// hint: Раздели [0, limit) на workers кусков; последний забирает остаток. Каждый воркер пишет в свой элемент слайса, потом сложи.
package main

import (
	"fmt"
	"runtime"
)

func isPrime(n int) bool {
	if n < 2 {
		return false
	}
	for d := 2; d*d <= n; d++ {
		if n%d == 0 {
			return false
		}
	}
	return true
}

// countPrimes считает простые числа меньше limit, разбив диапазон на workers частей,
// которые считаются параллельно.
func countPrimes(limit, workers int) int {
	panic("TODO")
}

func main() {
	const limit = 200_000
	fmt.Println("1 worker:", countPrimes(limit, 1))
	fmt.Println("7 workers:", countPrimes(limit, 7))
	fmt.Println("GOMAXPROCS workers:", countPrimes(limit, runtime.GOMAXPROCS(0)))
}
```

```go
// exercise: Первый ответ без утечки
// expect: winner: replica-2
// expect: goroutines: 1
// flags: race
// hint: Проигравшие горутины блокируются на ch <- навсегда: планировщик паркует их (состояние chan send), и GC их не соберёт.
// hint: Минимальная правка — буфер на всех отправителей: make(chan string, 3). Отправка не блокируется, горутины завершаются.
package main

import (
	"fmt"
	"runtime"
	"time"
)

func query(name string, d time.Duration) string {
	time.Sleep(d)
	return name
}

// first возвращает самый быстрый ответ из реплик.
func first() string {
	ch := make(chan string)
	go func() { ch <- query("replica-1", 100*time.Millisecond) }()
	go func() { ch <- query("replica-2", 10*time.Millisecond) }()
	go func() { ch <- query("replica-3", 50*time.Millisecond) }()
	return <-ch
}

func main() {
	fmt.Println("winner:", first())
	time.Sleep(200 * time.Millisecond)
	fmt.Println("goroutines:", runtime.NumGoroutine())
}
```
