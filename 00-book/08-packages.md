# Глава 8. Пакеты и дизайн кода

## Зачем

Синтаксис закончился. Эта глава о том, как из него собирается кодовая база, которую можно поддерживать годами командой:
границы пакетов, видимость, инициализация, раскладка проекта и идиомы. На senior-собеседовании это проверяют на этапе code review
и в вопросах «как бы ты организовал сервис».

---

## 1. Пакет как единица дизайна 🟢

- Пакет — это **абстракция с API**, а не «папка для файлов». Хорошее имя пакета короткое, в единственном числе, без подчёркиваний:
  `user`, `billing`, `httpx`. Плохие имена: `utils`, `common`, `helpers`, `models` — они ничего не говорят и притягивают всё подряд.
- Имя пакета — часть имени сущности: `user.Service`, а не `user.UserService`. `http.Server`, а не `http.HTTPServer`.
- Экспортируй **минимум**. Каждая экспортированная сущность — обещание обратной совместимости.
- Пакеты не должны знать друг о друге по кругу. Циклический импорт запрещён компилятором, и это помогает: зависимости вынужденно идут в одну сторону.

## 2. internal 🟢

Пакеты внутри каталога `internal/` можно импортировать только из дерева, корень которого — родитель `internal`:

```
promo/
├── cmd/promo/main.go          # может импортировать promo/internal/...
├── internal/billing/          # чужой модуль импортировать не сможет
└── pkg/client/                # публичный клиент (если он вообще нужен)
```

Это способ сказать «это не API» и проверить это компилятором. В сервисах почти весь код лежит в `internal/`.

## 3. Инициализация 🟡

Порядок: зависимости-пакеты (рекурсивно, каждый один раз) → переменные пакета в порядке зависимостей между ними → функции `init()` в порядке файлов и объявлений → `main()`.

```go
var defaultClient = newClient() // инициализация переменной пакета

func init() {
    // регистрация драйвера, кодека, метрик
}
```

- `init()` с побочными эффектами (сеть, файлы, чтение env) — code smell: такой пакет трудно тестировать, а ошибку из `init` можно только паникой.
  Конфигурацию и подключения создают **явно** в `main`.
- Глобальные изменяемые переменные (синглтоны) усложняют тесты и параллельный запуск. Передавай зависимости явно (глава 18).
- `import _ "pkg"` — импорт ради `init()`: `_ "net/http/pprof"`, драйверы `database/sql`.

## 4. Раскладка сервиса 🟡

Официального стандарта нет, и «golang-standards/project-layout» не является стандартом. Распространённая практичная схема:

```
promo-service/
├── cmd/
│   └── promo/main.go          # сборка зависимостей и запуск; логики нет
├── internal/
│   ├── domain/                # сущности и бизнес-правила, без зависимостей от инфраструктуры
│   ├── service/               # сценарии использования (use cases)
│   ├── storage/postgres/      # репозитории
│   ├── transport/http/        # хендлеры, DTO, маппинг ошибок
│   ├── transport/kafka/       # консьюмеры
│   └── config/
├── migrations/
├── api/                       # OpenAPI / proto
├── go.mod
└── Makefile
```

- Начинай с плоской структуры и дели, когда растёт. Маленький сервис с пятью слоями пустых пакетов хуже, чем один пакет на 500 строк.
- Альтернатива слоям — **деление по фичам** (`internal/wallet`, `internal/promotion`), где у каждой фичи свои хендлеры, сервис и хранилище.
  Для крупных сервисов это часто лучше: изменения фичи локальны.
- Подробнее про слои, DI и зависимости — в главе 18.

## 5. Дизайн API 🟡

- **Делай нулевое значение полезным** или давай конструктор `NewX(...)`, если без инициализации нельзя.
- Конструктор возвращает конкретный тип (`*Server`), а не интерфейс.
- Опции: обязательные параметры — аргументами, необязательные — структурой `Config` или функциональными опциями (глава 3).
- `context.Context` — первый параметр любой функции, которая делает IO или может долго работать.
- Не делай пакет, который сам запускает горутины «в фоне». Если без них нельзя, дай `Run(ctx)` или `Close()`, чтобы владелец управлял жизненным циклом.
- Синхронный API лучше асинхронного: вызывающий сам решит, запускать ли его в горутине. Обратное превратить сложнее.
- Не возвращай каналы и не принимай их без нужды: это усложняет контракт закрытия и отмены.
- **Документация:** комментарий перед экспортируемой сущностью начинается с её имени: `// Server handles ...`. Пакет описывается в `doc.go`.
  Примеры `func ExampleX()` в `_test.go` попадают в документацию и проверяются тестами.

## 6. Стиль, который ожидают на ревью 🟢

- `gofmt` и `goimports` — без обсуждений.
- Короткие имена в маленькой области видимости (`i`, `r`, `ctx`), описательные — в большой.
- Аббревиатуры одним регистром: `userID`, `HTTPClient`, `ServeHTTP`, а не `UserId` и `HttpClient`.
- Геттер без `Get`: `u.Name()`, а не `u.GetName()`. Интерфейс из одного метода называют по методу + `-er`: `Reader`, `Notifier`.
- Ранний выход вместо вложенности. Ошибка обрабатывается сразу после вызова.
- Комментарии объясняют **почему**, а не что.
- Источники: Effective Go, Go Code Review Comments, Google Go Style Guide, Uber Go Style Guide.

## 7. Рефлексия и unsafe — коротко 🔴

- `reflect` позволяет работать с типами во время выполнения: так устроены `encoding/json`, ORM, валидаторы. Цена — скорость (на порядок медленнее),
  отсутствие проверок при компиляции и паники вместо ошибок. В прикладном коде почти не нужен; дженерики закрыли многие старые сценарии.
- `unsafe` обходит систему типов: `unsafe.Pointer`, `unsafe.Sizeof`, `unsafe.String`, `unsafe.Slice`. Оправдан в узких местах производительности
  с доказанной пользой и комментарием. Правила преобразования `unsafe.Pointer` ↔ `uintptr` строгие: GC и копирование стека не знают, что `uintptr` — адрес.
- Кодогенерация (`go generate`: sqlc, mockgen, stringer, easyjson, protoc) — идиоматичная альтернатива рефлексии: ошибки ловятся при компиляции.

## Ловушки

- Пакет `utils` на 3000 строк, от которого зависит всё.
- Интерфейсы в пакете реализации и цикл импортов «service ↔ storage».
- `init()`, который ходит в сеть или читает env.
- Глобальный логгер, глобальная БД, глобальный конфиг.
- Пакет, который в конструкторе запускает горутину без способа её остановить.

## Закрепление

Упражнения запускаются прямо в панели (`make panel`, эта глава): правь код в редакторе и жми ▶ или <kbd>⌘/Ctrl+Enter</kbd>. Упражнение засчитывается, когда вывод совпал с ожидаемым; конкурентные прогоняются с `-race`. Подсказки открываются по одной — сначала попробуй без них.

```go
// exercise: Функциональные опции
// expect: addr=:8080 timeout=5s retries=3
// expect: addr=:9090 timeout=1s retries=5
// hint: Option — это func(*Server). NewServer заполняет значения по умолчанию, затем применяет опции по порядку.
// hint: Плюс подхода: новые параметры добавляются без поломки сигнатуры NewServer у всех вызывающих.
package main

import (
	"fmt"
	"time"
)

type Server struct {
	addr    string
	timeout time.Duration
	retries int
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { panic("TODO") }
func WithRetries(n int) Option           { panic("TODO") }

// NewServer: по умолчанию timeout = 5s, retries = 3.
func NewServer(addr string, opts ...Option) *Server {
	panic("TODO")
}

func (s *Server) String() string {
	return fmt.Sprintf("addr=%s timeout=%s retries=%d", s.addr, s.timeout, s.retries)
}

func main() {
	fmt.Println(NewServer(":8080"))
	fmt.Println(NewServer(":9090", WithTimeout(time.Second), WithRetries(5)))
}
```

```go
// exercise: Регистрация через init
// expect: drivers: [mysql postgres]
// expect: duplicate: driver "postgres" already registered
// hint: Переменные пакета инициализируются до любого init(), поэтому мапа drivers уже готова. init-функции идут сверху вниз.
// hint: Так устроен database/sql: драйвер регистрируется в init, а повторная регистрация — паника (ошибка программиста).
package main

import "fmt"

var drivers = map[string]bool{}

// Register паникует с сообщением `driver "name" already registered` при повторе.
func Register(name string) { panic("TODO") }

// Drivers возвращает имена по алфавиту.
func Drivers() []string { panic("TODO") }

func init() { Register("postgres") }
func init() { Register("mysql") }

func main() {
	fmt.Println("drivers:", Drivers())
	defer func() { fmt.Println("duplicate:", recover()) }()
	Register("postgres")
}
```
