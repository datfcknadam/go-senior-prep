# 03. Рантайм и производительность

На senior-уровне спрашивают «как оно работает» и «как ты нашёл и починил проблему с производительностью в проде».
Готовь 1–2 реальные истории: симптом → метрики → профиль → гипотеза → фикс → результат в цифрах.

> Подробно: [THEORY.md](THEORY.md) — планировщик, аллокатор и GC с объяснением, почему они так устроены.

## Планировщик (GMP)

- **G** — горутина, **M** — поток ОС, **P** — логический процессор (контекст исполнения), их `GOMAXPROCS` штук.
- У каждого P локальная очередь (256 G) + глобальная очередь. Свободный P **ворует** половину очереди у другого (work stealing).
- Блокирующий syscall: M уходит в syscall вместе с G, а P отдаётся другому M (handoff), чтобы не простаивал.
- Сетевой IO не блокирует M: горутина паркуется, а netpoller (epoll/kqueue) будит её при готовности сокета.
- Вытеснение: кооперативное (в прологе функций) + асинхронное по сигналу с Go 1.14 — тугой цикл без вызовов больше не вешает планировщик.
- **GOMAXPROCS в контейнере**: с Go 1.25 рантайм сам учитывает CPU limit cgroup. До этого — `go.uber.org/automaxprocs`,
  иначе при limit=2 и 64 ядрах на ноде — троттлинг CFS и рост латентности.

## Память и аллокации

- Аллокатор по мотивам TCMalloc: `mcache` (на P, без локов) → `mcentral` → `mheap`. Объекты делятся по ~68 size class.
- **Escape analysis**: компилятор решает, где жить переменной. На стеке — бесплатно, в куче — работа для GC.
  ```bash
  go build -gcflags='-m' ./...     # что и почему убегает в кучу
  ```
  Типичные причины побега: возврат указателя, сохранение в интерфейс, замыкание, слайс неизвестного на этапе компиляции размера, слишком большой объект.
- Сокращение аллокаций: предвыделять (`make(..., 0, n)`, `strings.Builder.Grow`), `sync.Pool` для буферов, избегать `[]byte ↔ string` в горячем пути,
  не упаковывать мелочь в `any`.

## Сборщик мусора

- Конкурентный, трёхцветный mark & sweep, без поколений и без перемещения объектов.
- Write barrier во время фазы маркировки; короткие STW-паузы (обычно десятки–сотни мкс).
- Когда запускается: `GOGC=100` → когда куча выросла на 100% от живой после прошлого цикла.
- `GOMEMLIMIT` (Go 1.19) — мягкий лимит памяти: GC работает чаще при приближении к лимиту. Ставят ~90% от limit контейнера, чтобы не словить OOMKill.
- Mark assist: горутина, которая много аллоцирует во время GC, сама помогает маркировать — отсюда всплески латентности.
- Green Tea GC (экспериментально в Go 1.25, по умолчанию в 1.26) — маркировка страницами для лучшей локальности. Знать, что есть.

## Профилирование

```go
import _ "net/http/pprof"   // на отдельном внутреннем порту!
```

```bash
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/profile?seconds=30   # CPU
go tool pprof -http=:8081 http://localhost:6060/debug/pprof/heap                  # память (inuse/alloc)
curl localhost:6060/debug/pprof/goroutine?debug=2                                  # стеки всех горутин — ищем утечки
go test -bench . -benchmem -cpuprofile cpu.out -memprofile mem.out
go tool trace trace.out                                                            # планировщик, GC, блокировки
```

- Профиль `block` и `mutex` нужно включить: `runtime.SetBlockProfileRate`, `runtime.SetMutexProfileFraction`.
- Сравнение бенчмарков — только через `benchstat` с `-count=10`, а не на глаз.
- PGO: положи CPU-профиль из прода как `default.pgo` в main-пакет — обычно +2–14% к CPU.

## Типичные истории «нашёл и починил»

| Симптом | Причина | Фикс |
|---|---|---|
| Растёт память, OOMKill | утечка горутин / подслайс большого буфера / мапа, которая не сжимается | goroutine-профиль, `slices.Clone`, пересоздание мапы |
| p99 скачет | частый GC из-за аллокаций в горячем пути | heap alloc_space профиль, пулы, предаллокация, `GOMEMLIMIT` |
| CPU в потолке, троттлинг | неверный GOMAXPROCS в контейнере | Go 1.25+ или automaxprocs |
| Горутины висят на мьютексе | один глобальный lock | шардирование, `atomic`, copy-on-write через `atomic.Pointer` |
| Много времени в `encoding/json` | рефлексия | кодогенерация (easyjson), или json/v2 |
