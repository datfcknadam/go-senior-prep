# Как это устроено внутри: структуры данных рантайма

Цель документа — чтобы ответы вида «слайс растёт ×2» или «nil-интерфейс ≠ nil-указатель» выводились из устройства, а не заучивались.
У каждого блока одна схема: **как лежит в памяти → что делает рантайм → почему так спроектировано → проверь сам**.

Исходники стоит открыть рядом (`go env GOROOT`, затем `src/...`):

| Что | Где |
|---|---|
| слайсы | `runtime/slice.go` (`growslice`, `nextslicecap`) |
| строки | `runtime/string.go` |
| мапы (Swiss, 1.24+) | `internal/runtime/maps/` (`map.go`, `table.go`, `group.go`) |
| мапы (старые) | `runtime/map.go` в Go ≤ 1.23 |
| интерфейсы | `runtime/iface.go`, `internal/abi/type.go`, `internal/abi/iface.go` |
| каналы, select | `runtime/chan.go`, `runtime/select.go` |
| defer, panic | `runtime/panic.go`, `cmd/compile/internal/ssagen` (open-coded) |
| стек горутины | `runtime/stack.go`, `runtime/runtime2.go` (`type g`) |

---

## 0. Базовые идеи, без которых остальное непонятно

1. **Компилятор знает размер и раскладку каждого типа.** Для каждого типа он генерирует дескриптор `abi.Type`
   (размер, выравнивание, `PtrBytes` — сколько байт с начала могут содержать указатели, битмапа указателей, хеш-функция, функция равенства, kind).
   На эти дескрипторы опираются рантайм, GC, интерфейсы и рефлексия.
2. **GC точный (precise).** Он знает, где в каждом объекте, в каждом кадре стека и в каждом регистре лежат указатели.
   Из этого следуют копируемые стеки (§7), запрет на хранение Go-указателей в C-памяти и правила `unsafe.Pointer`.
3. **Неизменяемость и value semantics упрощают рантайм.** Строки неизменяемы, поэтому их можно разделять без копий.
   Значения копируются, поэтому нет скрытого разделения состояния. Почти каждое «странное» правило языка следует из этих двух решений.

## 1. Слайс

### В памяти
```go
// runtime/slice.go
type slice struct {
    array unsafe.Pointer // указатель на первый элемент (не на начало массива!)
    len   int
    cap   int            // сколько элементов доступно от array до конца аллокации
}
```
`s[i:j]` создаёт новый заголовок: `array + i*elemsize`, `len = j-i`, `cap = oldcap - i`. **Аллокации нет, копии данных нет.**
Отсюда два следствия: подслайс видит те же данные, и подслайс держит живым весь исходный массив, потому что GC видит указатель внутрь аллокации,
а аллокация освобождается только целиком.

### Что делает `append`
Компилятор разворачивает `s = append(s, x)` примерно так:
```go
if len(s)+1 > cap(s) {
    s = growslice(s.array, len(s)+1, cap(s), 1, elemType) // новый массив, данные скопированы
}
s.array[len(s)] = x
s.len++
```
Внутри `growslice` → `nextslicecap`:
```go
func nextslicecap(newLen, oldCap int) int {
    newcap := oldCap
    doublecap := newcap + newcap
    if newLen > doublecap { return newLen }       // просят много — даём ровно сколько просят
    const threshold = 256
    if oldCap < threshold { return doublecap }    // маленькие — удваиваем
    for {
        newcap += (newcap + 3*threshold) >> 2     // плавный переход от ×2 к ×1.25
        if uint(newcap) >= uint(newLen) { break }
    }
    return newcap
}
```
Затем ёмкость в байтах **округляется вверх до size class** аллокатора (`roundupsize`), и cap пересчитывается из получившегося размера.

### Почему так
- **Геометрический рост** нужен, чтобы `append` в среднем стоил O(1). При росте на константу n вставок стоили бы O(n²) копирований.
  При росте в k раз суммарно копируется ≤ n·1/(k−1) элементов.
- **Почему не ×2 всегда:** большой слайс при удвоении теряет до 50% памяти впустую. Коэффициент 1.25 даёт ≤ 20% хвоста, ценой чуть более частых копирований.
  Формула с `3*threshold` сглаживает переход: раньше на 1024 был резкий скачок с ×2 на ×1.25, и рост не был монотонным.
- **Почему округление до size class:** аллокатор всё равно выдаст блок из ближайшего класса (§8 в рантайме), и лишние байты пропали бы.
  Поэтому их отдают в cap.
- **Почему `append` возвращает слайс, а не меняет аргумент:** заголовок передан по значению, и рантайм физически не может обновить переменную вызывающего.
  Отсюда же aliasing: если места хватило, два `append` от одного родителя пишут в одну ячейку.

### Проверь сам
```go
s := append([]int64(nil), 1, 2, 3, 4, 5)
fmt.Println(cap(s)) // 6: newLen 5 > 2*0 → 5 элементов = 40 байт → size class 48 → cap 6

var a []int
prev := -1
for i := 0; i < 2000; i++ {
    a = append(a, i)
    if cap(a) != prev { fmt.Print(cap(a), " "); prev = cap(a) }
}
// Go 1.26: 4 8 16 32 64 128 256 512 848 1280 1792 2560 — видно и удвоение, и формулу, и округление.
// Почему старт с 4, а не с 1: слайс не убегает в кучу, и компилятор (1.25+) берёт первый буфер
// на 32 байта прямо на стеке. Сделай a глобальной переменной, и последовательность начнётся с 1 2 4.

b := a[10:20]
fmt.Println(unsafe.SliceData(b) == &a[10]) // true — тот же массив
```

## 2. Строка

```go
type stringStruct struct {
    str unsafe.Pointer
    len int
}
```
- Байты строки лежат либо в read-only сегменте бинарника (литералы), либо в куче.
- `s[i:j]` даёт новый заголовок без копии, ровно как у слайса. Это безопасно **только потому, что строки неизменяемы**:
  никто не может поменять общие байты из-под другой строки.
- `[]byte(s)` обязан копировать: иначе через слайс можно было бы изменить «неизменяемую» строку, причём, возможно, литерал в read-only памяти, а это segfault.
  Обратная `string(b)` тоже копирует, иначе последующий `b[0] = 'x'` изменил бы строку.
  Компилятор убирает копию там, где доказано, что результат не переживёт выражение: `m[string(b)]`, `string(b) == "..."`.
- Для коротких временных конверсий есть буфер на стеке на 32 байта (`tmpBuf`), так что маленькие строки конвертируются без кучи.
- Конкатенация `a + b + c` компилируется в один вызов `concatstrings`: сначала считается суммарная длина, потом делается одна аллокация.
  А `s += x` в цикле — это новая аллокация и копия всего на каждой итерации.
- Сравнение строк: сначала длины, затем указатели (если указатель один и тот же, строки равны сразу), затем `memequal`.

## 3. Мапа (Swiss Tables, Go 1.24+)

### Идея открытой адресации
Старая мапа — это цепочки (бакет → overflow-бакет). Swiss table — **открытая адресация**: при коллизии ищем другой слот в той же таблице.
Главная проблема открытой адресации в том, что пробирование трогает много ключей, а каждое сравнение ключа может быть кеш-промахом.
Swiss table её решает так: **рядом с группой из 8 слотов лежат 8 байт метаданных**, и сначала сравниваются они, одной операцией над 8 байтами.

### В памяти
```
Map
 ├── seed (рандом на каждую мапу)
 ├── directory: []*table           ← extendible hashing
 │      table (≤ 1024 слотов)
 │        └── groups: [N]group
 │               group
 │                 ├── ctrl: uint64  ← 8 контрольных байт
 │                 └── slots: [8]{key, elem}
```
Контрольный байт слота:
- `0b1000_0000` — empty (пусто);
- `0b1111_1110` — deleted (надгробие, tombstone);
- `0b0hhh_hhhh` — full, где `h` — младшие 7 бит хеша (**H2**).

Хеш (64 бита) делится на две части: **H1** (старшие 57 бит) выбирает, с какой группы начать поиск, **H2** (7 бит) кладётся в контрольный байт.

**Маленькие мапы (≤ 8 элементов)** — это одна группа без таблиц и директории. Поиск сводится к сравнению 8 байт и ключей в одной кеш-линии.

### Поиск `m[k]`
```
hash := typ.Hasher(k, m.seed)
table := directory[hash >> (64 - globalDepth)]   // старшие биты выбирают таблицу
g := H1(hash) & (numGroups-1)                    // стартовая группа
for i := 0; ; i++ {                              // квадратичное пробирование по группам
    match := group[g].ctrl.matchH2(H2(hash))     // битмаска слотов с совпавшим H2
    for slot in match {
        if key[slot] == k { return elem[slot] }  // настоящее сравнение — только тут
    }
    if group[g].ctrl.matchEmpty() != 0 {
        return notFound                          // встретили пустой слот — ключа точно нет
    }
    g = (g + i + 1) & mask
}
```
`matchH2` — это битовый трюк, SWAR («SIMD within a register»): XOR контрольного слова с H2, размноженным на 8 байт,
затем поиск нулевых байт выражением `(x - 0x0101..) & ^x & 0x8080..`. На amd64 вместо этого используются SSE-инструкции.
Ложное совпадение по 7 битам бывает с вероятностью 1/128 на слот, так что ключи сравниваются почти только у нужного слота.

### Удаление и надгробия
Почему нельзя просто пометить слот пустым? Потому что поиск **останавливается на пустом слоте**. Если ключ X при вставке
прошёл мимо заполненной группы G дальше, а потом в G освободили слот и пометили его empty, поиск X остановится на G и не найдёт его.
Поэтому:
- если в группе уже есть пустой слот, цепочку пробирования через неё никто не продолжал, и слот можно сделать empty;
- иначе ставится **deleted**: поиск идёт дальше, а вставка может переиспользовать этот слот.
Надгробия расходуют `growthLeft`, и при накоплении таблица перестраивается.

### Рост
- Максимальная загрузка 7/8. Когда `growthLeft == 0`:
  - если таблица меньше 1024 слотов, она перестраивается в таблицу двойного размера;
  - если уже 1024, она **делится на две** (`localDepth+1`). Директория удваивается только при `localDepth == globalDepth`.
- **Почему так:** перестройка затрагивает максимум 1024 слота, поэтому пауза одной вставки ограничена, даже если в мапе 100 млн ключей.
  Старая мапа решала ту же проблему иначе — постепенной эвакуацией (см. ниже).

### Почему быстрее старой
- 8 кандидатов отсекаются одним сравнением, ключи трогаются почти только при настоящем совпадении → меньше кеш-промахов.
- Нет overflow-цепочек и указателей на них.
- Load factor 7/8 против 6.5/8 → меньше памяти.

### Старая мапа (≤ 1.23), её до сих пор спрашивают
```go
type hmap struct {
    count     int
    flags     uint8          // в т.ч. hashWriting — для детекта конкурентной записи
    B         uint8          // бакетов 2^B
    hash0     uint32         // seed
    buckets   unsafe.Pointer
    oldbuckets unsafe.Pointer // не nil во время роста
    nevacuate uintptr         // прогресс эвакуации
}
type bmap struct {           // бакет
    tophash [8]uint8         // старшие 8 бит хеша каждого слота
    // keys   [8]K           // ключи подряд, потом значения подряд —
    // values [8]V           // так меньше паддинга, чем пары {K,V}
    // overflow *bmap
}
```
Младшие B бит хеша выбирают бакет, а `tophash` быстро отсекает слоты. Рост начинается, когда средняя загрузка > 6.5 или слишком много overflow
(тогда «рост на месте», чтобы уплотнить). **Эвакуация инкрементальна:** каждая запись переносит 1–2 старых бакета, а чтение во время роста смотрит в `oldbuckets`.

### Из устройства следуют правила
| Правило | Почему |
|---|---|
| нельзя `&m[k]` | слот переезжает при росте или делении таблицы, указатель повис бы |
| нельзя `m[k].f = 1` | `m[k]` — копия значения, а не адресуемая переменная |
| случайный порядок | seed на каждую мапу + случайная стартовая позиция итератора; плюс порядок и так меняется при росте |
| `fatal`, а не panic, при гонке | флаг `writing` ловит гонку уже после порчи структуры, а продолжать с битой таблицей опасно |
| не сжимается | слоты и группы не освобождаются при удалении, только при пересоздании |
| ключ должен быть comparable | нужны `Hasher` и `Equal` из дескриптора типа |
| NaN-ключ не найти | `NaN != NaN`, сравнение в поиске всегда ложно |

### Проверь сам
```go
// Мапа — указатель: размер переменной = 8 байт.
var m map[string]int
fmt.Println(unsafe.Sizeof(m)) // 8

// Не сжимается:
m = make(map[int][128]byte)
for i := range 1_000_000 { m[i] = [128]byte{} }
for i := range 1_000_000 { delete(m, i) }
runtime.GC()
// runtime.ReadMemStats → HeapInuse почти не уменьшился. А после m = nil; runtime.GC() — уменьшился.
```
Бенчмарк: `go test -bench . -benchmem`, сравни с `GOEXPERIMENT=noswissmap` (есть в 1.24–1.25).

## 4. Интерфейс

### В памяти
```go
type iface struct {          // непустой интерфейс (error, io.Reader)
    tab  *itab
    data unsafe.Pointer
}
type eface struct {          // any
    _type *_type
    data  unsafe.Pointer
}
type itab struct {
    inter *interfacetype     // какой интерфейс
    _type *_type             // какой конкретный тип
    hash  uint32             // копия _type.hash — для type switch
    fun   [1]uintptr         // таблица методов переменной длины; fun[0]==0 → тип не реализует
}
```

### Что лежит в `data`
Интерфейс — два машинных слова, поэтому значение в него **не помещается** (кроме pointer-shaped). Возможны варианты:
- указатель, мапа, канал, функция или структура из одного указателя — кладутся **прямо в `data`**;
- всё остальное (int, string, структура) копируется в кучу через `runtime.convT*`, и `data` указывает на копию.
  Исключения без аллокации: нулевые значения и однобайтовые значения (`staticuint64s`), а также константы, которые компилятор кладёт в read-only данные.

Отсюда:
- **Упаковка в интерфейс почти всегда аллокация**, и поэтому `fmt.Println(x)` или `log(any)` в горячем пути — источник нагрузки на GC.
- **Значение в интерфейсе — копия.** Изменить исходную переменную через него нельзя.

### Почему `T` не реализует интерфейс с методом на `*T`
В `data` лежит копия `T`, которой нет ни в одной переменной. Если бы рантайм вызвал на ней метод `*T`, метод изменил бы анонимную копию,
и изменение молча потерялось бы. Язык запрещает это на уровне method set. Обратное разрешено:
у `*T` есть методы `T`, потому что компилятор генерирует обёртку, которая разыменовывает указатель и вызывает метод на значении.

### Как строится `itab`
- Методы в дескрипторе типа и в дескрипторе интерфейса **отсортированы по имени**, поэтому сопоставление идёт слиянием двух списков за O(n+m).
- Если пара (интерфейс, тип) известна при компиляции (`var r io.Reader = f`), itab генерируется статически.
- Если нет (assertion `x.(io.Reader)` из `any`), рантайм ищет пару в глобальной хеш-таблице `itabTable`, при промахе строит itab и кладёт туда.
  Начиная с Go 1.22 у каждого места assertion есть свой маленький кеш.

### Операции
| Операция | Стоимость |
|---|---|
| вызов метода `r.Read(p)` | загрузить `tab.fun[i]` и сделать косвенный вызов с `data` в качестве ресивера. Инлайна нет, зато есть возможная девиртуализация (PGO) |
| `x.(*T)` (к конкретному типу) | одно сравнение указателя `tab` (или `_type`) с ожидаемым |
| `x.(io.Reader)` (к интерфейсу) | поиск или построение itab |
| type switch | сравнение `hash`, затем типа, а для многих веток бинарный поиск по хешу |
| `a == b` для интерфейсов | равны типы, затем `_type.Equal(data, data)`; если тип несравним — **panic** |

### Nil-интерфейс — из определения
`err == nil` означает `tab == nil && data == nil`. Строка `var p *MyErr; var err error = p` записывает в `tab` itab пары (error, *MyErr),
а в `data` — nil. Первое слово не nil, значит и интерфейс не nil. Запоминать тут нечего, это просто сравнение двух слов.

### Проверь сам
```go
type eface struct{ typ, data unsafe.Pointer }

var p *int
var a any = p
e := (*eface)(unsafe.Pointer(&a))
fmt.Println(e.typ != nil, e.data == nil) // true true → a != nil

// Аллокации при упаковке (sink — глобальная var sink any, чтобы значение точно убегало):
n := 1000
fmt.Println(testing.AllocsPerRun(1000, func() { sink = n }))  // 1 — int копируется в кучу
fmt.Println(testing.AllocsPerRun(1000, func() { sink = &n })) // 0 — указатель кладётся прямо в data
```
`go build -gcflags=-m` покажет `... escapes to heap` на упаковке в интерфейс.

## 5. Структура

- Поля лежат **подряд в порядке объявления**, Go не переупорядочивает их, в отличие от Rust. Каждое поле выровнено по своему `Alignof`,
  размер структуры кратен максимальному выравниванию, чтобы в массиве у каждого элемента было правильное выравнивание.
  ```go
  type Bad struct {
      a bool  // offset 0, затем 7 байт паддинга
      b int64 // offset 8
      c bool  // offset 16, затем 7 байт паддинга до кратности 8
  } // Sizeof = 24
  ```
  `unsafe.Offsetof(x.b)` и `unsafe.Alignof` показывают это явно.
- **Почему порядок важен не только для размера:** GC сканирует объект только до последнего поля с указателем (`PtrBytes`).
  Если указатели стоят в начале, хвост скалярных полей GC не трогает. А объект совсем без указателей попадает в noscan span, и GC его вообще не сканирует.
- **Нулевой размер:** все аллокации размера 0 возвращают адрес `runtime.zerobase`, поэтому `&struct{}{} == &struct{}{}` может быть и true, и false
  (спецификация не гарантирует ни того, ни другого).
- **Встраивание** физически означает обычное поле, лежащее внутри. Продвижение методов — работа компилятора: `outer.M()` превращается в `outer.Inner.M()`.
  Динамической диспетчеризации нет, поэтому «переопределить» метод для кода внутри `Inner` нельзя.
- **Пустые методы и обёртки:** если `Outer` встраивает `*Inner` и попадает в интерфейс, компилятор генерирует метод-обёртку `Outer.M`,
  который вызывает `Inner.M`. Если `Inner == nil`, получится panic уже внутри.

## 6. Канал и select

Структура `hchan` и алгоритм send/recv разобраны в [02-concurrency/THEORY.md](../02-concurrency/THEORY.md#3-каналы-изнутри). Здесь только то, что объясняет «почему».

- **Прямая передача в стек ждущей горутины.** Если получатель уже ждёт, отправитель копирует значение прямо в переменную получателя (`sudog.elem`).
  Это одна копия вместо двух через буфер. Это **единственное место**, где одна горутина пишет в стек другой. Безопасно оно потому, что получатель запаркован,
  а его стек не двигается: стек можно сжать или скопировать, только когда горутина в безопасной точке, и рантайм это учитывает.
- **Почему `close` дважды или отправка в закрытый канал — panic, а приём — нет:** приём из закрытого канала — штатный сигнал «данных больше нет».
  А отправка после закрытия означает, что программа потеряла знание о владении каналом. Это ошибка программиста, и в таких случаях Go паникует.
- **`selectgo` в три прохода:**
  1. Перемешивает `pollorder` (случайный порядок проверки веток, отсюда случайный выбор) и сортирует `lockorder` по **адресу канала**.
     Все каналы select'а блокируются в этом порядке, а единый порядок захвата исключает дедлок между двумя select'ами на тех же каналах.
  2. Ищет готовую ветку в `pollorder`. Если нашлась, операция выполняется и всё разблокируется. Если ветки нет, но есть `default`, выполняется `default`.
  3. Иначе ставит `sudog` горутины в очереди **всех** каналов и паркуется. Когда кто-то её разбудил через один канал,
     она снимает свои `sudog` с остальных.
  Поэтому select на 10 каналов дороже select на 2: на каждом проходе блокируются все.

## 7. Стек горутины и почему он может «переезжать»

```go
type g struct {
    stack       stack   // [lo, hi)
    stackguard0 uintptr // граница для проверки в прологе; также флаг вытеснения
    m           *m      // поток, на котором выполняется
    sched       gobuf   // сохранённые SP, PC и т.д. при парковке
    atomicstatus atomic.Uint32 // _Grunnable, _Grunning, _Gwaiting, _Gsyscall...
    // ...
}
```
- В **прологе почти каждой функции** компилятор вставляет проверку `if SP < g.stackguard0 { morestack() }`.
- `morestack` → `newstack`: выделяется стек **вдвое больше**, старый **копируется**, а все указатели, ведущие внутрь стека, сдвигаются на разницу адресов.
  Рантайм находит эти указатели по stack maps — метаданным компилятора о том, где в каждом кадре лежат указатели. Это и есть пункт 2 из §0.
- **Почему копирование, а не «сегменты»:** до Go 1.3 стеки были сегментированными, и вызов на границе сегмента в горячем цикле постоянно
  выделял и освобождал сегмент (hot split). Копирование даёт амортизированно O(1) и непрерывную память.
- Во время GC стек может **сжаться** вдвое, если используется меньше четверти.
- **Вытеснение использует ту же проверку:** чтобы попросить горутину уступить, рантайм пишет в `stackguard0` специальное значение `stackPreempt`.
  Ближайший пролог «думает», что стек кончился, идёт в `morestack` и там уступает процессор. Тугой цикл без вызовов функций пролога не проходит,
  поэтому с 1.14 добавлено асинхронное вытеснение сигналом `SIGURG`.
- Следствия:
  - указатель на переменную стека нельзя отдать в C (cgo проверяет это правилами передачи указателей), потому что стек может переехать;
  - `unsafe.Pointer` → `uintptr` → обратно в разных выражениях опасно: GC и копирование стека не знают, что `uintptr` — адрес.

## 8. defer и panic

- **Open-coded defers (1.14+).** Если в функции ≤ 8 defer'ов и ни одного в цикле, компилятор вставляет вызовы отложенных функций **прямо в каждую точку выхода**,
  а какие defer'ы «взведены», хранится в битовой маске на стеке. Стоимость почти как у обычного вызова.
- Иначе (defer в цикле) создаётся запись `_defer` в связном списке горутины. Это медленнее, и записи живут до выхода из функции.
- **Аргументы вычисляются в момент `defer`**, потому что они сохраняются в запись или в слоты стека прямо тогда. Замыкание сохраняет ссылки на переменные,
  поэтому видит их финальные значения.
- **Как именованный результат меняется в defer:** `return x` компилируется в «записать x в слот результата → выполнить defer'ы → RET».
  Defer видит слот результата как переменную и может его переписать.
- **panic:** рантайм создаёт `_panic`, раскручивает стек и выполняет defer'ы. Если defer вызвал `recover()`, паника помечается recovered, а выполнение
  продолжается так, будто функция с этим defer'ом вернулась нормально (с текущими значениями именованных результатов).
  `recover` проверяет, что его вызвали непосредственно из defer'а, обрабатывающего панику, поэтому из вложенной функции он вернёт nil.

## 9. Дженерики изнутри

- Полная мономорфизация (как C++/Rust) раздувает бинарник, а полный боксинг (как Java) медленный. Go выбрал середину: **GC shape stenciling**.
- **Форма (shape)** — underlying type, при этом все указатели считаются одной формой `*uint8`.
  `Max[int]` и `Max[int64]` получат разный код, а `Max[*User]` и `Max[*Order]` — один экземпляр.
- Каждому экземпляру передаётся скрытый аргумент — **словарь**: дескрипторы реальных типов, itab'ы для методов ограничения, вспомогательные функции.
- **Следствие для производительности:** вызов метода ограничения у указательного типа идёт через словарь, то есть как вызов через интерфейс,
  а компилятор часто не может такое заинлайнить. Поэтому `func Sum[T Number](...)` по `int` летает,
  а `func Process[T Stringer](x T)` с указателями не быстрее, чем просто `func Process(x fmt.Stringer)`.

## 10. Как это рассказывать на собеседовании

Плохо: «мапа — хеш-таблица, порядок случайный».
Хорошо: «С 1.24 мапа — Swiss table: группы по 8 слотов с контрольным словом из 7-битных фрагментов хеша. Поиск сравнивает 8 байт разом и трогает ключ
только при совпадении, так что меньше кеш-промахов. Таблицы ограничены 1024 слотами и делятся при росте, поэтому латентность вставки ограничена.
Адрес элемента взять нельзя, потому что слоты переезжают при росте, а порядок обхода рандомизирован специально».

Схема ответа: **структура → операция → почему → следствие для кода**. Если интервьюер копает глубже, у тебя есть следующий уровень.
