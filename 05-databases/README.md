# 05. Базы данных

Основная СУБД в типичном Go-бэкенде — PostgreSQL. Ещё встречаются Redis, ClickHouse (аналитика), Kafka как шина событий,
поисковые движки. На senior-собеседовании спрашивают про Postgres глубоко, а про остальное — на уровне «когда и зачем».

## Индексы

- **B-tree** — по умолчанию: `=`, `<`, `>`, `BETWEEN`, `ORDER BY`, префиксный `LIKE 'abc%'` (при подходящем collation / `text_pattern_ops`).
- **Hash** — только `=`. **GIN** — массивы, `jsonb`, полнотекстовый поиск, триграммы (`pg_trgm`). **GiST** — геоданные, диапазоны. **BRIN** — огромные таблицы, где данные физически упорядочены (логи по времени).
- **Составной индекс** `(a, b, c)` работает для условий по `a`, `a,b`, `a,b,c` — правило левого префикса. Сначала колонки с равенством, потом с диапазоном.
- **Покрывающий индекс**: `INCLUDE (...)` → Index Only Scan без похода в таблицу (если visibility map свежая — нужен VACUUM).
- **Частичный индекс**: `WHERE status = 'active'` — меньше и быстрее, если запросы всегда с этим условием.
- Индекс по выражению: `lower(email)`.
- Цена индексов: замедляют запись, занимают место, мешают HOT-update.
- `CREATE INDEX CONCURRENTLY` на проде — без долгой блокировки записи (но не внутри транзакции и может оставить INVALID-индекс).

## EXPLAIN

```sql
EXPLAIN (ANALYZE, BUFFERS) SELECT ...;
```

- Seq Scan / Index Scan / Index Only Scan / Bitmap Heap Scan — когда какой и почему планировщик может выбрать Seq Scan, даже если индекс есть (низкая селективность, маленькая таблица, устаревшая статистика).
- Join: Nested Loop (мало строк снаружи + индекс внутри), Hash Join (большие наборы, равенство), Merge Join (оба входа отсортированы).
- Сравнивай `rows` (оценка) с `actual rows` — большое расхождение = плохая статистика → `ANALYZE`.

## Транзакции и изоляция

| Уровень | Dirty read | Non-repeatable read | Phantom | Serialization anomaly |
|---|---|---|---|---|
| Read Committed (по умолчанию в PG) | нет | **да** | **да** | **да** |
| Repeatable Read (в PG — snapshot isolation) | нет | нет | нет* | **да** (write skew) |
| Serializable (SSI) | нет | нет | нет | нет |

\* В Postgres RR не допускает фантомов — сильнее стандарта.

- **Lost update**: два `SELECT` → вычисление в приложении → `UPDATE`. Решения: атомарный `UPDATE ... SET x = x + 1`, `SELECT ... FOR UPDATE`, оптимистическая блокировка через `version`.
- **Write skew** (классика с дежурными врачами): каждая транзакция читает и пишет разные строки. Лечится Serializable или явной блокировкой.
- В RR и Serializable приложение **обязано** ретраить транзакцию при `40001 serialization_failure`.

## MVCC

- Каждая версия строки (tuple) имеет `xmin` / `xmax`. `UPDATE` = новая версия + пометка старой. Читатели не блокируют писателей.
- Мёртвые версии убирает **VACUUM** (autovacuum). Долгие транзакции мешают VACUUM → **bloat** таблиц и индексов.
- **Transaction ID wraparound** — 32-битный счётчик; если VACUUM не успевает «замораживать» строки, база уходит в read-only.
- HOT update — если не менялись индексированные колонки и на странице есть место, индексы не трогаются (`fillfactor`).

## Блокировки

- Строковые: `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, `FOR KEY SHARE`. `SKIP LOCKED` — очередь задач в таблице. `NOWAIT`.
- Табличные: `ALTER TABLE` берёт `ACCESS EXCLUSIVE` и **встаёт в очередь** — за ним блокируются все `SELECT`. На проде: `SET lock_timeout = '2s'` + ретраи миграции.
- Advisory locks — распределённая блокировка средствами БД.
- Дедлоки: PG находит через `deadlock_timeout` и откатывает одну транзакцию. Профилактика — единый порядок захвата.

## Масштабирование

- **Пул соединений**: процесс на соединение в PG дорогой → PgBouncer в transaction mode (осторожно с prepared statements и session-уровнем). В Go: `pgxpool`, `MaxConns` ≤ лимит базы / число подов.
- **Реплики**: асинхронная репликация → replication lag → read-your-writes ломается. Решения: читать из мастера после записи, sticky по пользователю, ждать LSN.
- **Партиционирование** (внутри одного инстанса): по времени (логи, события) или хешу. Partition pruning, удаление старых данных через `DROP PARTITION`.
- **Шардирование** (между инстансами): ключ шардирования (user_id, item_id), consistent hashing, перешардирование, кросс-шардовые запросы и транзакции — главная боль.

## Go и база

- `database/sql` / `pgx`: всегда `rows.Close()` и проверка `rows.Err()`; контекст на каждый запрос.
- Транзакция: `defer tx.Rollback(ctx)` сразу после `Begin` — после `Commit` он безопасен (no-op).
- N+1 запросов — классика ревью. Батчинг, `= ANY($1)`.
- Миграции — обратная совместимость с предыдущей версией кода (expand → migrate → contract).

## Redis / Kafka — минимум для senior

- Redis: однопоточное выполнение команд, структуры данных, TTL и политики вытеснения, persistence (RDB/AOF), Redis Cluster (16384 слота), распределённый лок и почему Redlock спорный.
- Kafka: топик → партиции → упорядоченность только внутри партиции (ключ сообщения!), consumer group, ребалансировка, offset commit,
  at-least-once по умолчанию → консьюмер должен быть **идемпотентным**. Exactly-once — только внутри Kafka (транзакции).
